# BR-ASDLC-016 — A red gate always produces urgent work served to an agent, never a silence.

Status: Enforced

## Rule

Once a candidate's gate run concluded red and its one automatic rerun of runner aborts and known flakes has settled (its latest attempt is a rerun that completed red, or the rerun workflow `release.gate_rerun_workflow` ran for its first attempt and every such run completed; the bridge cannot read whether a rerun will come, so until then it waits), or once no run of the rerun workflow showed up within `release.gate_rerun_wait_minutes` (default 30) of the gate run's completion (the rerun workflow may be absent or broken; the ticket then says no rerun was seen, and a rerun run that showed up and is still running keeps the wait), the bridge opens one gate-fix ticket for that candidate: a child of the release issue, labelled with the release label, assigned to the release fixer `release.fix_assignee` (unassigned, taken by role, when the key is unset or the tracker does not know it), in Ready, urgent, carrying the hidden marker `spl-asdlc:gate-fix candidate=<tag>` by which it is found again whatever its state, so that it is never opened twice. Its contract is complete: the gate green on the release branch, the failing suites read from `results/suites.json` of the evidence pack and the link to the gate run (an evidence pack that cannot be read still opens the ticket, which says the failing suites are unknown), no new feature and no change beyond what the failure needs, the acceptance criterion the failing suites passing on the release branch (the listed suites, or the suites that failed in the gate run when they are unknown), an ordinary box the implementer ticks once verified on that branch, `No new rule.`. The ticket follows the flow of any ticket: To Deploy at its fix's merge (BR-ASDLC-008), Done at the release's closure. The gate of the next candidate is the verification: a still-red one opens a new gate-fix ticket for that candidate. When the newest candidate's gate is green, the bridge closes Done, with a comment naming that candidate, every gate-fix ticket of the cycle that never reached a merge, still in Triage, Backlog, Ready or In Progress (a rerun made the gate green, say); any other is left alone, and the bridge ticks no box of it. A green or pending gate opens nothing, and a red gate older than `stagnation_hours` raises the stagnation notice as well (`docs/spec/05-release-cycle.md` §3).

## Evidence

The owner's decision of 2026-10-08: the source chain's `notify-gate-failure` CI job, which created a fix task, was dropped at the extraction (CI never writes to the tracker) and nothing replaced it, so a red gate stalled the cycle in silence. The owner's decision of the same day: a bounded wait, so that an absent or broken rerun workflow cannot hold the ticket back. The owner's decision of 2026-10-09: the gate-fix ticket is an ordinary ticket whose criterion its implementer ticks, and the next gate is the verification, so no box is the bridge's to tick. The owner's decision on QA findings (2026-10-14): the gate-fix ticket goes to the same release fixer as a blocking QA finding's ticket (BR-ASDLC-022).
