# SPL-ASDLC business rules

Format: one row per rule. A rule is `Enforced` only when the named test runs in CI; until then it is `Proposed`. Ids are `BR-ASDLC-NNN` and are never reused.

| ID | Rule | Evidence | Test | Status |
|---|---|---|---|---|
| BR-ASDLC-001 | **The repository carries no instance data.** No name of a product, agent, person, organisation member or installation that uses the method appears anywhere in the repository (code, docs, tests, workflows, fixtures), and no identifier of an installation does either: e-mail addresses, `/home/<user>` or `/Users/<user>` paths, 9+-digit account or chat ids, hexadecimal uids, GitHub App bot logins. Allowed: product values that hold for every install (this product's repository slug and crate name), and the names of the integrations the method supports as adapters or hosts (trackers such as Linear, Jira or Livela; runtimes such as AgentForge, Claude Code or Codex; hosts such as GitHub). The line is: an integration is named, an installation is not. | The method must be reusable by anyone, and publishable, without a scrub. | `scripts/check-no-instance-names.sh`: scans every tracked file for the identifier forms above, and for the words listed in the environment variable `SPL_ASDLC_FORBIDDEN_WORDS` (comma-separated; kept outside the repository, in a CI secret or a local untracked file, precisely so that the list itself never enters the repository). Zero hits, no baseline, no exemption list. | Enforced |
| BR-ASDLC-002 | **A ticket leaves Post Deploy for Done at the bridge's tick, once every box of its `## Post deploy` section is checked; there is no verb.** Checking the boxes, once verified in production, is the whole gesture. At each tick the bridge reads the tickets labelled `post-deploy-validation/<product>` that are still in Post Deploy and moves to Done each one whose Done gate is ok (its boxes and its duplicates'), then removes the label; a ticket with one box still open stays in Post Deploy, and the bridge writes nothing but a missing validation sub-task; a read that fails moves nothing and is reported. | The owner's decision of 2026-10-07: the closure comment named a `release post-release-check` verb the bridge does not have, so nothing ever moved a ticket out of Post Deploy (`docs/open-points.md` #1). | `tick::release_tests::a_post_deploy_ticket_moves_to_done_at_the_tick_that_finds_every_box_checked`, `tick::release_tests::a_partially_checked_post_deploy_ticket_stays_in_post_deploy`, `tick::release_tests::an_unreadable_read_moves_nothing_and_is_reported`, `tick::release_tests::a_ticket_resolved_by_hand_loses_the_index_label_once`, `method::release::closure::tests::the_closure_comment_names_what_stays_open_and_why` | Enforced |
| BR-ASDLC-003 | **Post Deploy stays outside the in-progress group; its verification is served through a validation sub-task.** The ticket in Post Deploy is never served to an implementer. When the bridge moves a ticket into Post Deploy it creates, once, a validation sub-task under it: unassigned, in Ready (a followed status), with a complete contract and the hidden marker `spl-asdlc:post-deploy-validation parent=<id>`, by which it is found again among the ticket's children (a lost answer is found, never created twice; a refused creation is retried at a later tick). The sub-task asks its agent to verify the parent's `## Post deploy` boxes in production, check the ones it can verify and close the sub-task; a check that needs a human or is beyond the agent is named in a comment and the sub-task is reassigned to the owner (`owner.tracker_user`), so a human finishes. | The owner's decision of 2026-10-07: post-release verification needs someone to do it, and the validation states are never served (`docs/spec/03-vocabulary.md`). | `tick::release_tests::the_closure_moves_a_ticket_to_post_deploy_with_one_unassigned_validation_sub_task`, `tick::release_tests::a_lost_creation_answer_is_found_and_the_sub_task_never_created_twice`, `tick::release_tests::a_refused_validation_sub_task_is_created_at_a_later_tick_once`, `method::texts::tests::the_post_deploy_validation_sub_task_is_a_contract_marked_as_the_bridges`, `method::vocabulary::tests::post_deploy_stays_outside_the_in_progress_group` | Enforced |
| BR-ASDLC-004 | **Release angle sub-items and the brief are created only once the candidate's gate is green, never at the release item's creation.** The release item, the candidate's record and the embarked labels come at the first tick after the cut; the angle sub-items, the consolidation item and the brief of a candidate wait for that candidate's own gate run to conclude `success`, and the brief links that run and its evidence pack. A red, pending or unreadable gate, or a brief whose facts (evidence pack included) cannot be read, opens nothing; each later RC waits for its own gate. | An agent never starts on a candidate the deterministic layer refused, and never without the brief that links the gate's evidence (spec 05 §2–§3, REQ-REL-046/048). | `src/tick/release_tests.rs`: `a_red_gate_opens_the_release_item_but_no_angle_nor_brief`, `the_gate_turning_green_opens_the_round_once_with_the_evidence`, `a_later_candidate_with_a_red_gate_waits_again`, `an_unreadable_gate_writes_nothing_more_and_says_why`, `a_green_gate_whose_evidence_cannot_be_read_opens_nothing`. | Enforced |
| BR-ASDLC-005 | **Every PR is independently deployable.** A merged PR can ship to production at any time, even when it does not close its ticket: the release embarks its ticket whatever the ticket's state (but Canceled), and the closure judges only a ticket in To Deploy or Post Deploy, leaving one still In Progress or In Review to its next PR (`docs/spec/04-pr-review.md` §10, `docs/spec/05-release-cycle.md` §2, §11). | Owner's decision on several PRs per ticket (2026-10-07): a PR may not close its ticket, so each one must stand by itself. | Enforced by review, not by code: the angle reviewer checks it (`docs/agents/review-pr.md` step 3) and the coordinator requests changes on a PR that is not self-standing (`docs/agents/consolidate.md` step 4). The bridge's side, shipping a merged PR whatever its ticket's state, is tested by `tick::release_tests::a_merged_pr_ships_while_its_ticket_is_still_in_progress`. | Proposed |
| BR-ASDLC-006 | **One PR per ticket by default.** A ticket has as many commits as needed and one PR; a second PR needs a real reason, which its implementer records in the ticket's comments (`docs/spec/00-overview.md` invariant 2, `docs/spec/01-ticket-contract.md` §7). A PR is linked to exactly one ticket. | Owner's decision on several PRs per ticket (2026-10-07), reconciling spec 00 §2 and spec 01 §7. | Enforced by the agent protocols, not by code: the implementer records the reason (`docs/agents/implement.md` step 8); the reviewer reads it and, when everything should have been one PR, records why on the ticket and the coordinator requests changes (`docs/agents/review-pr.md` step 3). The bridge's side, a ticket with several PRs handled per PR, is tested by `tick::tests::while_another_pr_is_in_review_the_ticket_stays_in_review`. | Proposed |
| BR-ASDLC-007 | **A review round is scoped to its PR.** Its angle sub-items and its consolidation item close when that PR resolves, Done at a merge and Canceled at a close without merge, whatever becomes of the ticket, which stays open for a later PR; a ticket In Review for another of its PRs gives a new PR its own round (`docs/spec/04-pr-review.md` §3, §10). | Owner's decision on several PRs per ticket (2026-10-07): a round left open after its PR resolved would be served to a reviewer with nothing to review. | `tick::tests::a_rounds_items_close_when_its_pr_merges_while_the_ticket_stays_open`, `tick::tests::a_rounds_items_are_canceled_when_its_pr_is_closed_unmerged_while_the_ticket_stays_open`, `tick::tests::while_another_pr_is_in_review_the_ticket_stays_in_review`, `tick::tests::a_pr_closed_unmerged_leaves_the_ticket_in_review_while_another_is_reviewed` | Enforced |
| BR-ASDLC-008 | **The state of a ticket follows its PRs, by two rules in order.** Whenever a PR of a ticket resolves, or a ticket past the merge has an open PR: (1) the review rule has priority, another PR of the ticket in review keeps it In Review, a PR sent back by the coordinator puts it In Progress; (2) the completeness rule, with no PR in review a ticket whose boxes (the `## Post deploy` section apart) are not all ticked goes back In Progress; then an open PR on a complete ticket keeps it In Review (REQ-MERGE-028); only a ticket with every box ticked, nothing open and a PR merged goes To Deploy. When an open PR's ticket could not be read, nothing is written (`docs/spec/04-pr-review.md` §10). | Owner's decision on several PRs per ticket (2026-10-07). | `method::ticket_state::tests::*`, `method::contract::tests::the_boxes_before_deploy_set_the_post_deploy_section_apart`, `tick::tests::a_merge_that_leaves_a_box_open_sends_the_ticket_back_to_work`, `tick::tests::a_merge_with_every_box_checked_goes_to_deploy_once`, `tick::tests::a_second_pr_on_a_ticket_past_the_merge_brings_it_back_to_review`, `tick::tests::changes_requested_on_one_pr_wait_while_another_is_in_review`, `tick::tests::an_unreadable_ticket_of_another_pr_holds_the_state_after_a_merge` | Enforced |
| BR-ASDLC-009 | **A ticket the closure returns to In Progress is unassigned; the agent system handles reprise by role, with nobody named.** Whether the closure sends it back for its Done gate or for a cited rule the registry lacks, the bridge clears the assignee in the same write as the state, and says so in its comment; it never keeps the ticket on its current assignee and never resolves someone to hand it to (no rework assignee, no author marker). Rework is distributed by being pickable. A replay finds the ticket In Progress and writes nothing (`docs/spec/05-release-cycle.md` §11, REQ-REL-089). | The owner's decision on `docs/open-points.md` #9 (2026-10-07). | `tick::release_tests::the_closure_reopens_an_incomplete_ticket_unassigned_once`, `tick::release_tests::the_closure_reopens_a_ticket_citing_an_unknown_rule_unassigned`, `tick::release_tests::a_dry_run_of_the_closure_prints_the_unassign`, `method::done_gate::tests::a_reopened_ticket_is_said_unassigned_with_nobody_named`, `tracker::linear::tests::a_status_write_can_unassign_in_the_same_write`, `tracker::livela::tests::a_status_write_can_unassign_and_a_replay_leaves_no_fact` | Enforced |
| BR-ASDLC-010 | **The public `spl-asdlc` crate depends on no consumer (no `livela-core`): each runtime/tracker writes its own wrapper on its side, depending on `spl-asdlc` by version. The dependency arrow always points toward ASDLC, never outward.** The Livela runner's `BridgeJob` and its store glue live in the runner's code; this crate offers the pass, the adapter and the `LivelaStore` slice they need (`docs/livela-contract.md` §3). No dependency of the manifest, `[patch]` or `[replace]` included, is a Livela crate or a Git source, and `Cargo.lock` holds neither. | The owner's decision of 2026-10-07 (`docs/open-points.md` #11): the Livela repository is private and unlicensed, a Git dependency would name an account in `Cargo.lock` (BR-ASDLC-001), and a second copy of the core would give `BridgeJob` a trait the runner does not know. | `tests/dependency_arrow.rs`: `the_manifest_depends_on_no_consumer_and_on_no_git_source`, `the_lockfile_holds_no_consumer_and_no_git_source`, `a_consumer_is_recognised_however_it_is_spelled` | Enforced |
| BR-ASDLC-011 | **The bridge is the sole writer of item transitions and writes them regardless of any agent lock; an advisory lock protects an agent's work on the item's content, never its status.** The bridge neither waits for a lock to be released nor notifies its holder of a transition (`docs/livela-contract.md` §6). | The owner's decision of 2026-10-07 (`docs/open-points.md` #12): Livela locks are advisory and the core's writes do not check them; a transition held back by a lock would stall the method on an agent's session. | Enforced by review, not by code: the `LivelaStore` slice the adapter is written against has no lock surface, so the adapter (`src/tracker/livela.rs`) cannot read, wait on or answer a lock, and its in-memory test store does not model locks. A test would need the contract to expose locks to the adapter, which this rule says it must not use. | Proposed |
| BR-ASDLC-012 | **Everything served to an agent carries a full contract; the consolidation generates one for the nits work rather than any runtime exempting it by marker.** The nits work is written with a goal (triage: classify each nit as kept or dropped, never presume it fixed; a dropped nit is closed with its reason), non-goals, the nits as boxes under `## Acceptance criteria`, each saying what was observed, where and in what context, and `No new rule.` under `## Business rules`, whether it is one shared ticket per release or one ticket per nit (`release.nits`). A shared nits ticket that carries no contract (an older format) is left alone and said, never written into. | The owner's decision of 2026-10-07: the bridge wrote the shared nits ticket as bare checkbox lines, which a contract guard at pickup refused (`docs/open-points.md` #14, spec 05 §6). | `method::release::findings::tests::the_shared_nits_ticket_is_a_contract_whose_goal_is_to_triage`, `method::release::findings::tests::a_nit_ticket_of_its_own_is_a_contract_keyed_like_a_finding`, `method::release::findings::tests::a_nit_goes_under_the_acceptance_criteria_once_and_the_ticket_stays_a_contract`, `method::release::findings::tests::a_nits_ticket_without_a_contract_is_left_alone`, `tick::release_tests::the_shared_nits_ticket_is_a_full_contract_that_asks_to_triage`, `tick::release_tests::per_nit_grouping_files_one_contract_ticket_per_nit_in_triage_once`, `tick::release_tests::a_nits_ticket_of_the_older_format_is_left_alone_and_said`, `config::tests::the_nits_grouping_is_shared_or_per_nit_and_nothing_else` | Enforced |
| BR-ASDLC-013 | **The consolidation agent documents problems, it does not solve them (it may note an already-obvious solution, never hunt for one).** For each nit it makes sure the report captures, as faithfully as it can, what was observed, where and in what context; whether the nit is kept or dropped is left to the agent who takes the nits work up at refinement. The rule covers the release QA, where nits accumulate into nits work; at a PR review the coordinator still applies the fixes it retains, nits included (`docs/agents/consolidate.md`, PR review, step 3), so a PR's nit never becomes a ticket. | The owner's decision of 2026-10-07 on the nits work (`docs/open-points.md` #14), and its scope confirmed by the owner the same day: fixed at the PR, accumulated at the QA. | Enforced by the agent protocols, not by code: `docs/agents/consolidate.md` (release candidate, step 2) and `docs/agents/review-release.md` step 3; spec 06 rule 5 says what each field of a nit carries. | Proposed |
