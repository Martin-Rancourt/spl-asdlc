# Open method points

Points the specification leaves open, raised to the owner. Until each is decided, the bridge does the fail-closed thing given here: it waits, and it invents nothing. When a point is settled, the specification says so and the entry moves to "Decided" below, with where the specification now says it. Numbers are never reused; 13 was withdrawn before it was written.

| # | Point | Until decided |
|---|---|---|
| 3 | The human GO: the owner's `/go` on the release item is a tracker comment, but spec 08 names `owner.github_login`. The approval is not implemented (spec 05 §8, 08 rule 4, 09). | Under `go_policy = "human"` the GO is never given; a person tags and publishes the release by hand instead (spec 09). |
| 4 | Whose approval counts as the human one under `review.human_approval`. | A PR that needs it is not merged; `review.human_reviewer` is asked once. |
| 8 | The format of "one more pass" allowed in the release issue (`max_rc_passes` raised for one cycle). Not implemented (spec 05 §10, 09). | Only the configured `max_rc_passes` counts: one more pass is allowed by raising it in the configuration. |
| 10 | A rewritten tracking row on trackers that can edit comments (REQ-MERGE-069). | No row on any tracker: informational facts stay in the action log. |

## Decided

| # | Point | Decision |
|---|---|---|
| 1 | Who moves a ticket from Post Deploy to Done, and when. | **Decided by the owner (2026-10-07)**: no verb; the bridge moves the ticket to Done at the tick that finds every `## Post deploy` box checked, and the closure creates a validation sub-task for each ticket it moves to Post Deploy (spec 03, 05 §11, 07, 09; BR-ASDLC-002, BR-ASDLC-003). Implemented as specified. |
| 2 | Release angle sub-items and the brief: at the creation of the release item (spec 05 §2), or once the gate of the candidate is green (spec 05 §3, REQ-REL-046/048). | **Decided by the owner**: once the candidate's gate is green, never at the release item's creation; spec 05 §2–§3 say so, BR-ASDLC-004 enforces it. |
| 5 | Several PRs per ticket, the end of a review round, REQ-MERGE-028. | **Decided** (2026-10-07): one PR per ticket by default, every PR independently deployable, a round scoped to its PR, and the state rules in order: `docs/spec/04-pr-review.md` §10, BR-ASDLC-005…008. A PR claimed by several tickets still waits: a PR implements exactly one ticket. |
| 6 | Writing a finding's ticket id back into the merged report (spec 06 rule 4 against spec 09). | **Decided by the owner (2026-10-12)**: no write-back; the finding marker on the ticket (candidate, angle, finding id) carries the mapping, and the report's `ticket` stays as the angle wrote it (spec 06 rule 4). |
| 7 | Whether `ticket check` moves a complete Triage or Backlog ticket to Ready (spec 03). | **Decided by the owner (2026-10-12)**: no; `ticket check` stays read-only. Ready is set by refinement, a person or the refinement agent once the contract is verified; an implementer never changes a status (spec 03, 09; `docs/agents/refine-ticket.md`). |
| 9 | The implementer a reopened ticket goes back to at closure (REQ-REL-089). | **Decided by the owner (2026-10-07)**: nobody; a ticket the closure returns to In Progress is always unassigned, and the agent system resumes it by role (spec 05 §11; BR-ASDLC-009). Implemented as specified. |
| 11 | Where the public crate gets `livela-core` from, so that `BridgeJob` implements the runner's trait. | **Decided by the owner (2026-10-07)**: nowhere; `spl-asdlc` depends on no consumer, the arrow goes from Livela to ASDLC. The `BridgeJob` wrapper and the store glue live in the runner's code and depend on `spl-asdlc` by version (`docs/livela-contract.md` §3, `docs/setup/tracker-livela.md`; BR-ASDLC-010). |
| 12 | Whether the bridge may write a transition on an item an agent holds locked (Livela locks are advisory). | **Decided by the owner (2026-10-07)**: it writes, whoever holds the lock; the bridge is the only automated writer of transitions, and a lock protects an agent's work on the content, never the status. No waiting, no notification (`docs/livela-contract.md` §6; BR-ASDLC-011). Implemented as specified. |
| 14 | The nits work: the bridge wrote the shared nits ticket as bare checkbox lines, which a contract guard at pickup refuses. | **Decided by the owner (2026-10-07)**: the consolidation always writes the nits work with a full contract, never a marker-based exemption; its goal is to triage each nit (kept or dropped), not to presume it fixed; the consolidation documents a nit, it does not solve it (spec 05 §6, 06 rule 5, 08; BR-ASDLC-012, BR-ASDLC-013). Implemented as specified; a shared nits ticket without a contract is left alone and said at each tick. **Superseded by the owner's decision on QA findings (2026-10-14, BR-ASDLC-022)**: a release finding is blocking or non-blocking, and a non-blocking one becomes an ordinary ticket of its own, with a full contract; there is no shared nits ticket and no grouping setting. The code and the specification are aligned later. |
| 15 | The release QA round under BR-ASDLC-018: blocking its consolidation item by the candidate's angle sub-items would deadlock the cycle, because a release angle sub-item closes only when its angle PR is merged, and that merge needs the coordinator's approval, which the consolidation item is what serves (`docs/agents/consolidate.md`, release candidate, step 4). Either the bridge closes a release angle sub-item once its angle PR carries a valid report (the angle has reported), and then the relations apply, or the release round keeps no relation and the bridge holds the angle PRs' merges until every offered angle has reported. | **Decided by the owner (2026-10-09)**: neither. A release angle sub-item follows the normal flow (In Progress, In Review once its angle PR is ready and green, back In Progress on a coordinator's changes requested, Done when the bridge merges the PR, never To Deploy); the coordinator reviews each angle PR as it comes, as its reviewer, served by assignment (the angle sub-item, set In Review, is assigned to `release.coordinator_assignee` in the same write, and sent back In Progress to its angle's assignee, or to nobody); the candidate's consolidation item is blocked by every angle sub-item of the candidate and is the overall review, served once every angle PR is merged, Done when a newer candidate is tagged or the release is published (spec 03, 05 §3–§5, 06, 07; `docs/agents/consolidate.md`, `docs/agents/review-release.md`; BR-ASDLC-020). Implemented as specified. |
