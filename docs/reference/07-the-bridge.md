# 07 — The bridge

One deterministic process, `spl-asdlc tick`, that turns GitHub facts into tracker state and tracker state into GitHub actions. It is the only automated writer of the statuses the flow derives from GitHub (`03-vocabulary.md` says who writes each); it never owns a step, and a person may take any of them by hand (`09-requalification-and-human-gestures.md`). It contains no model call.

## Invariants

1. **It runs in the user's environment**, never in CI: a daemon or scheduled job (a tracker's own runner, a cron, a system timer), or by hand (`spl-asdlc tick` from a shell or a skill). The same binary and the same configuration serve every host.
2. **It polls GitHub**, at the interval its host chooses (Livela runs it on its own; with another tracker, a timer on the host does; `bridge.poll_minutes` is only a hint, `docs/setup/bridge.md`). Nothing needs to be exposed on the network; an optional relay can push webhook events into a queue the bridge pulls, which only shortens the latency.
3. **It writes under one identity**: a GitHub App installed on the repositories (the same App the CI workflows use), with a fallback to a personal token where an App is not allowed; the tracker identity is a service account of the tracker. The binary prints under which names it writes.
4. **Every write is idempotent.** The bridge keeps an action log (append-only, one line per decision: when, repository, object, action, inputs, outcome). A fact already acted upon is skipped; a fact whose action failed is retried at the next tick; a tracker read that fails writes nothing and retries. On unix the log is private to the bridge's account: the file is created `0600`, a directory the bridge creates for it `0700` (`docs/setup/bridge.md`, "Action log").
5. **It fails closed.** An unreadable configuration, registry, ticket or PR link stops the decision that depends on it and says so in the log; it never guesses and never degrades to "no constraint".
6. **One merge per repository per tick**, so that the next tick re-reads a base that moved.
7. **It leaves no heartbeat in the data.** A tick that finds nothing to do writes nothing, anywhere, but the action log's note of why a PR waits, when that reason is new (step 3). A tick that works leaves only its effects (transitions, comments, links, merges), signed by its identity: that is its report. It never rewrites an unchanged value. A failed tick (error, time budget exceeded) is reported once to its host (the host's job log, the action log), never as a fact on an item. The lock file of invariant 8 is no exception: it is empty and carries nothing.
8. **One tick at a time per repository.** A tick holds an exclusive lock (`flock`, the system's file lock) on a file beside its action log, `<log>.lock`, from before it reads the repository's facts to its end. A second tick on the same repository (a timer and a run by hand overlapping) finds the lock taken, takes no decision and writes nothing, says that a tick is already running, and exits 0. The lock goes with the process, so a tick that crashes leaves none behind; the file stays in place, empty. A dry run writes nothing and takes no lock. One host runs the bridge for a repository: the lock is not shared across hosts. A system without `flock` (Windows) takes no lock: there, its host keeps one tick at a time.

## What a tick does, in order, per configured repository

1. **Read**: open PRs (state, draft, base, head SHA, checks, reviews, threads, labels, linked ticket), release branches and RC tags with their annotations, gate runs per tag (with their attempt) and the evidence artifact, the runs of the gate's rerun workflow, the CHANGELOG the cut prepared at the candidate, release tags and published releases, merged merge-backs; recent merged PRs for the sweep.
2. **Release coordination** (`05-release-cycle.md`): new branch + tag → release issue, candidate record, labels; RC tagged → candidate record, labels, the previous candidate's consolidation item Done; gate of that RC green → its angle sub-items, consolidation item blocked by each of them (BR-ASDLC-020), then its brief linking the gate's evidence (never before, BR-ASDLC-004; a relation not laid holds the brief to a later tick) and the release note written into the release issue, and the gate-fix tickets it made moot (none of their PRs merged) closed; gate of that RC red once its automatic rerun settled, or `gate_rerun_wait_minutes` after its completion with no rerun seen → one urgent gate-fix ticket under the release issue, carrying the failing suites of the evidence pack (BR-ASDLC-016); angle PR opened (a draft angle PR is out of the flow) → its sub-item In Progress; angle PR green → its sub-item In Review, assigned to `release.coordinator_assignee` in the same write; changes requested by a coordinator at its head → its sub-item In Progress, assigned to its angle's assignee (or unassigned); angle PR approved with a valid report → the Apps' requests for changes the approval supersedes dismissed as for any PR (a person's holds it, `04-pr-review.md` §6), then merge into the release branch, its sub-item Done, tickets from the report; GO reached → the release note in the release issue (written again when it is missing, the GO held while it cannot be), the release tag on the latest candidate's commit, then its GitHub release with the notes the cut prepared (a tag or a release a person made by hand is taken as done, never made again; a tag on another commit stops the GO; the closure records who published the release, spec 09); release published → the consolidation items Done; release published and merge-back merged → closure and release note, then the archiving of what the cycle resolved (never an open item, the release issue last; a failed archive retried at the next tick, BR-ASDLC-019); passes exhausted with blockers → escalation.
3. **PR review coordination** (`04-pr-review.md`): a draft PR is out of the flow: ignored entirely, nothing written for it, its CI not read (none runs on it), never merged, counted for nothing among its ticket's PRs (`04-pr-review.md` §1); a required check is green only by a success, never skipped or neutral (a draft run's skipped `required-check` holds the PR marked ready until its ready run succeeds); PR opened → its ticket In Review at once, before CI, from Backlog, Ready or In Progress (In Progress is the implementer's: the bridge never writes it when a branch or a PR appears); PR ready and green with a complete contract and a box ticked → angle sub-items, consolidation item blocked by each of them (BR-ASDLC-018), and In Review for a ticket sent back; review submitted → sub-item done; coordinator approved with every angle sub-item of the round closed and checks green and threads resolved → each App's standing request for changes that approval supersedes dismissed (its message naming the approval and the head SHA; a person's is never dismissed and holds the PR), then merge (the merge comment stating only the conditions that applied), the PR's round closed, the ticket To Deploy (for a ticket with nothing to deploy, `tracker.no_deploy_label`: Done, or Post Deploy with its validation sub-task while its own `## Post deploy` boxes wait), or where the state rules of `04-pr-review.md` §10 put it; changes requested by a coordinator at the head → In Progress, unless another PR of the ticket is in review; an open PR on a ticket past the merge → the ticket back where §10 puts it; a PR that gets no angle (no PR review, `04-pr-review.md` §11) → no round, merged on its CI and the other merge conditions with no approval, logged as a merge with no PR review; a round opened under an earlier configuration that no longer asks for some of its angles, or for any → the items no longer asked canceled, each with a comment saying so, and the merge conditions those of the current plan. A PR the pass holds (no ticket, a draft (out of the flow), checks not green, an incomplete contract, a conflict, behind a base it must be up to date with, no qualifying coordinator approval at the head, a standing request for changes (a person's: `waiting: pr#<n> changes requested by <login> (a person; the bridge never dismisses it)`), an angle sub-item of its round still open (BR-ASDLC-018), unresolved threads, a hold of its review plan, a human approval missing, ready but not the one merge of the tick) is reported with its reason, one line per PR and tick in the tick's report, `waiting: pr#<n> <reason>` (for instance `waiting: pr#30 no coordinator approval at <head12> (approvals from: <login>, <login>)`), the dry run included. Waiting writes nothing to GitHub or the tracker; the action log notes it (outcome `waiting`) only when the reason or the head of that PR changes, never once per tick.
4. **Sweep**: PRs merged outside the bridge in the last 24 hours get the same transitions, once; the round of every PR merged or closed without merge in that window is closed, and a ticket left In Review by a PR closed without merge goes where `04-pr-review.md` §10 puts it.
5. **Post-deploy validation** (`05-release-cycle.md` §11): every ticket labelled `post-deploy-validation/<product>` and still in Post Deploy whose `## Post deploy` boxes are all checked (the Done gate) → Done, and the label removed; one that still waits gets its validation sub-task, urgent (BR-ASDLC-017), if it has none (found by its marker among the ticket's children, never created twice); a resolved ticket loses the label. No verb.
6. **Write the action log**, then exit (or sleep until the next tick when run as a daemon).

## What it reads on GitHub (the facts)

| Fact | Where |
|---|---|
| PR readiness, checks, reviews, threads, labels, head SHA, base, up-to-date | Pull request API, checks API, review threads |
| Linked ticket | The tracker's attachment for the PR URL (tracker side), or the item URL in the PR body as a fallback declared by configuration |
| Release branch, RC tag, class | Refs and annotated tag message |
| Gate result and evidence pack | Workflow run on the tag's SHA and its attempt; artifact `release-gate-evidence-<sha>`, and `results/suites.json` inside it for a red gate |
| A red gate's automatic rerun | The `workflow_run` runs of `release.gate_rerun_workflow` created from the gate run's completion until `release.gate_rerun_wait_minutes` after it (GitHub runs them on the default branch's head, not the tag's SHA) |
| Angle report | The file `.spl-asdlc/qa/<candidate>/<angle>.json` at the angle PR's head |
| Release notes | The version's section of `CHANGELOG.md` at the candidate, prepared by the cut (`release prepare`) |
| Release tag, published release | Tags and the Releases API, the release's author |
| Merge-back | PR from `release/*` into `main`, merged |

## What it writes to the tracker (the `Tracker` trait)

Read an item and its description; create an item (with parent, labels, assignee hint, priority); set a status by canonical name; add a label; comment; add a relation (`blocks`, `duplicate`); link an item to a PR URL and find an item by a PR URL; list the children of an item; find the release issue of a product and version; list items by label; archive a resolved item at the closure of its cycle (`05-release-cycle.md` §11: what the closure archives and what it never archives). Archiving is a capability of the tracker: Linear archives (the issue stays searchable and restorable, never deleted); a tracker that counts no open items against a limit (Livela) says it does not archive, and the bridge asks it for nothing. Nothing else. Every text it writes is English. A description is written only when its text changed as the tracker stores it: a tracker restyles the markdown it keeps (Linear turns `- ` bullets into `* `, adds or drops blank lines, trims trailing spaces), so a description that differs from the bridge's only in that is unchanged and never rewritten (invariant 7), the release note block of the release item included.

An item it serves to an agent is a complete contract that carries its protocol (BR-ASDLC-015): an angle sub-item or a consolidation item, of a PR review or of a release candidate, embeds the method's protocol of its job under a `## Protocol` section, compiled into the binary (`04-pr-review.md` §3, `05-release-cycle.md` §3), and says what closes it in the bridge's terms. The item is frozen at its creation: found again by its marker, it is never rewritten, so a later bridge's protocol never changes an open item. Before it creates one, the bridge looks among the parent's children for the item by its marker **or** by its exact title (REQ-REL-048), so that a marker an agent edited never makes it create the item twice. Every item stays well under the tracker's description size (a conservative 60 000 characters, which a test holds the longest item to); a protocol that would outgrow it is trimmed in its file, never cut in the item.

## What it writes to GitHub

Merges (REST, pinned to a head SHA), branch deletions, labels, comments on PRs (one per cause, never repeated), the dismissal of an App's standing request for changes that a coordinator's approval at the head supersedes, right before the merge (`04-pr-review.md` §6), the update of a PR branch behind a base it must be up to date with (`review.require_up_to_date`), a review request to `review.human_reviewer` for a green PR held by something only a human can lift, the dispatch of the cut workflow when the policy tags the next RC automatically, and on a computed GO the annotated release tag and its GitHub release. The ticket it opens for an App's PR that has none (`review.ticketless_authors`, `04-pr-review.md` §9) is a tracker write: created labelled `ticketless-pr` and linked to the PR there.

## What it sends (the `Notifier` trait)

Notices go through the channels of `[[notify]]` that take their event (spec 08); the tracker or PR comment stays the durable record (`05-release-cycle.md` §12). A notice that no configured channel takes has **nothing to send**: that is a project's choice, not a failure. The notice is done: the bridge writes its comment (with its marker) once, which is all it says of it, and never retries it; the release note of a closure says so on the release item, and the closure goes on. A channel that takes the event and fails, or that cannot be built on the host (a secret reference that resolves to nothing), is a failure: logged, reported by the tick, retried at the next tick, never marked sent.

## Verbs

| Verb | Purpose |
|---|---|
| `tick` | One pass; `--dry-run` writes only the log of what it would do |
| `release cut --product <p> [--open]` | Dispatch the cut workflow (new cycle or next RC). A configuration without a `[release]` section is refused by every verb |
| `release status --product <p>` | The GO decision and its inputs, as text and JSON (exit 0 on a GO, 1 otherwise); once the newest candidate's cycle is closed, that no cycle is in flight and which release closed the last one (exit 0) |
| `release prepare [--version <X.Y.Z>] [--notes <file>] [--dir <path>] [--repository <owner>/<repo>] [--date <YYYY-MM-DD>] [--dry-run]` | Run by the cut's `open` in a checkout of the new release branch: the next version from the commits since the last release, along the git graph, written into the version files and the CHANGELOG, and the release notes; prints `version=`, `tag=`, `previous-tag=`. Reads the repository's file only, never an instance overlay, and talks to no service (`05-release-cycle.md` §1) |
| `release requalify <ticket> --blocking <true\|false> --reason <r>` | Human requalification of a finding: blocking or not |
| `release abandon --product <p>` | Abandon the cycle in flight (`05-release-cycle.md` §13) |
| `ticket check <item>` | Contract judgement |
| `config check` | Validate `.spl-asdlc/config.toml` (the default of every `--file`), merged with its instance overlay (spec 08) |
| `doctor` | Verify the setup of a repository (App, secrets, rulesets, tracker identity, config and its instance overlay); `release cycle` (its QA angles, or none), and `release base`: the published release the next candidate is measured from, or none yet, the first release being measured from the repository's root |
