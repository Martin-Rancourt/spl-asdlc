# 05 — The release cycle

Exhaustive, on the whole project, in release candidates. The bridge coordinates; agents and humans do the QA on branches; the GO is computed.

Every project has the cycle: a configuration without a `[release]` section is refused (`08-configuration.md` rule 11). What is optional is its QA: a cycle with `release.angles = []` has no QA angle, and its GO rests on the release CI (§3). A merged ticket waits To Deploy for the next release; only a ticket with nothing to deploy goes straight to Done at its merge (`docs/method.md`, "Merge").

## Invariants

1. **A human opens a cycle.** The cut is a `workflow_dispatch` of the `release-cut` workflow (`open`): it creates the release branch `release/<YYYY-MM-DD-HH-MM>-utc` from `main`, refuses when a release branch is already in flight, **prepares the release** on it with `spl-asdlc release prepare` (the published binary of the channel the caller names, its checksum verified), commits `chore(release): v<X.Y.Z>` and pushes the branch and its first RC tag, annotated with the release class, in one atomic push. The preparation follows the git graph, never dates: the version is computed from the commits of `<last release tag>..HEAD` (Conventional Commits; a breaking change, `!` or `BREAKING CHANGE`, bumps the major from 1.0, a `feat` the minor, anything else the CHANGELOG lists the patch; before 1.0 a breaking change or a `feat` bumps the minor and the rest the patch; with no earlier release the whole history is read and the version bumped from `0.0.0`; `--version` forces one), written into the version files (Rust's `Cargo.toml` and `Cargo.lock` natively, any other through `release.version_files`), and the CHANGELOG gets the version's section in the Conventional Commits CHANGELOG format, as release-please writes it (the heading with its compare link, then `### ⚠ BREAKING CHANGES` and one section per type of `release.changelog_sections`, each entry with its PR and commit links), which is also the release notes. A range with nothing to release (no Conventional Commit of a listed type, no breaking change) is refused, and nothing is created. A commit merged into `main` while the previous cycle was open, which only the merge-back brought into this range, is in this release's notes by construction. **No job waits for another workflow's run**, so one runner is enough. Every later candidate is a `candidate` dispatched on the release branch (`--ref release/<stamp>-utc`), never on `main`, which tags rc.N+1 on its tip: the version is already committed there. Nothing else happens in CI.
2. **The release issue follows at the next tick.** The bridge sees the new branch and tag, creates the **release issue** (title: product and the version its candidate tag names), records the candidate on it and labels every embarked ticket `release/<product>-v<version>` whatever its state but Canceled (every merged PR is deployable, `04-pr-review.md` §10); the bridge's own review items linked to the same PRs are not embarked tickets (§11), nor is a ticket with nothing to deploy (the no-deploy label, `04-pr-review.md` §10), which its merge delivered. Nothing starts before the issue exists, so a tag without an issue is harmless. The angle sub-items and the brief wait for the gate (§3).
3. **The gate judges the frozen tag.** The `release-gate` workflow runs the project's suites on the RC tag, writes `results/suites.json`, uploads the evidence pack, and fails closed on any skipped or absent suite. QA does not start on a red gate. **Once the candidate's own gate run is green**, and never before, the bridge creates one **angle sub-item** per configured release angle and one **consolidation item** for that candidate (each angle sub-item assigned to its angle's `assignee`, the consolidation item to the coordinator named by `release.coordinator_assignee`, an agent the tracker serves; an unset or unknown participant leaves the item unassigned, and completing the round never reassigns an existing item; an angle sub-item is then reassigned by its flow only, §4), the consolidation item **blocked by every angle sub-item of the candidate** through the tracker's own `blocks` relation (BR-ASDLC-020), then posts the **brief**, which links the gate run and its evidence pack. The relations are written right after the items and before the brief; a relation already there is not written again, and an open consolidation item missing a relation gets it at the next tick. A relation that cannot be read or written is reported and **holds the brief**, fail-closed: the items stay, but the brief, which is what starts the angles' work, is not posted that tick; the next tick lays the missing relations and only then posts the brief, once. So no angle starts while its consolidation item could be served before it. So the consolidation item is served only once every angle sub-item is resolved, that is once every angle PR is merged (§5). A red, pending or unreadable gate opens no angle and no brief; each new RC waits for its own gate in the same way.
    **A release may have no QA angle.** A project that writes `release.angles = []` (`08-configuration.md`) runs the cycle without a QA round: the release item, its candidate record, the embarked labels, the gate and its gate-fix tickets, the GO's tag and release, the publication and the closure are as above; once the candidate's gate is green the bridge opens no angle sub-item and no consolidation item and posts the brief alone, which says that no QA angle is configured. The candidate's record says so too, with the marker `spl-asdlc:no-qa-angle candidate=<tag>`: angles configured later apply from the next candidate, never to one recorded with none. The gate stays: it is the release's minimum.
    **A red gate is never a silence** (BR-ASDLC-016): an **implementer** fixes it on the release branch, from a **gate-fix ticket** the bridge opens. Once the candidate's gate run concluded red and its one automatic rerun of runner aborts and known flakes has settled (the run's latest attempt is a rerun that completed red, or the rerun workflow `release.gate_rerun_workflow` ran for its first attempt and every such run completed; until then the bridge waits, since it cannot read whether a rerun will come), **or no run of the rerun workflow showed up within `release.gate_rerun_wait_minutes` (default 30) of the gate run's completion** (the rerun workflow may be absent or broken: the ticket then says no rerun was seen; a rerun run that showed up and is still running keeps the wait, whatever the bound), the bridge opens **one gate-fix ticket per candidate**, found again by its marker `spl-asdlc:gate-fix candidate=<tag>` among the release issue's children whatever its state, never twice: a child of the release issue, labelled `release/<product>-v<version>`, assigned to the release fixer `release.fix_assignee` (**unassigned** when the key is unset or the tracker does not know it, so that an implementer takes it by role), in **Ready**, **urgent**. Its contract is complete: the goal is the gate green on the release branch; the failing suites are read from `results/suites.json` of the evidence pack, with the link to the gate run (an evidence pack that cannot be read still opens the ticket, which says the failing suites are unknown and links the run); the non-goals are no new feature and no change beyond what the failure needs; the acceptance is the failing suites passing on the release branch (the listed suites, or the suites that failed in the gate run when they are unknown), an ordinary box the implementer ticks once it verified it on that branch, as any criterion; `No new rule.` under `## Business rules`. The fix is a PR whose base is the release branch (`docs/agents/implement.md` step 2); the next RC is cut by the coordinator, or by the bridge when `auto_candidate = true` (§7). The ticket follows the flow of any ticket: **To Deploy** at its fix's merge (`04-pr-review.md` §10), **Done** at the release's closure (§11). The gate of the next candidate is the verification: when it is red too, the bridge opens a new gate-fix ticket for that candidate, as above. When the gate of the newest candidate is green, the bridge closes every gate-fix ticket of the cycle opened for it or an earlier candidate that never reached a merge, still in Triage, Backlog, Ready or In Progress (a rerun made the gate green, say): **Done**, with a comment naming the green candidate. Any other is left alone: In Review (its PR is being judged), past the merge (the closure judges it, §11) or already resolved. A red gate older than `stagnation_hours` raises the stagnation notice as well, once.
    **Each item carries its protocol** (BR-ASDLC-015), as in a PR review (`04-pr-review.md` §3): beside its contract and what closes it in the bridge's terms, an angle sub-item embeds `docs/agents/review-release.md`, the angle's file `docs/agents/angles/<angle>.md` (or, for an angle of the project's own, a line saying the method has no notes for it) and the schema and rules of the angle report (`06-qa-report.md`); the consolidation item embeds `docs/agents/consolidate.md` and the same schema and rules. The project's angle notes are linked, never embedded. The texts are compiled into the bridge: an item carries the protocol of the bridge version that created it and keeps it while open, since an item found again by its marker is never rewritten (it is found by its exact title among the release issue's children as well, so that an edited marker never makes the bridge create it twice, REQ-REL-048); a later candidate's items carry the protocol of the bridge that creates them. An angle sub-item closes when the bridge merges its angle PR (§5); the consolidation item when a newer candidate is tagged or the release is published, or else at the closure (§5, §11).
4. **Each angle works on its own branch.** The reviewer of an angle cuts `qa/<candidate>/<angle>` from the release branch, reviews the whole project from its angle (with the brief, the evidence pack, the tag annotation and the diff as orientation), classifies each finding as blocking or not and documents it, fixes nothing, commits its **angle report** (`06-qa-report.md`, mandatory even when nothing was found) and nothing else, and opens a PR to the release branch whose body names its sub-item. The angle sub-item follows the normal flow of a work item (BR-ASDLC-020): **In Progress** when the angle's work starts (the bridge, when its angle PR is opened; a draft angle PR is out of the flow, as any draft, and drives nothing), **In Review** when that PR's required checks are green, back **In Progress** when a configured coordinator requests changes on it at its head, and **Done** when the bridge merges it, or finds it merged by a person (spec 09). The bridge serves the coordinator by assignment: the write that sets In Review also assigns the item to `release.coordinator_assignee`, so the coordinator is served the review of that angle PR (unset or unknown to the tracker: the status is written and the assignee left as it is); the write that sends it back In Progress assigns it to its angle's `assignee`, or to nobody when none is configured or the tracker does not know it (taken by role); Done leaves the assignee as it is. A status and assignee already right are not written again. An angle PR that names no sub-item is neither followed nor merged, and is told once per head, on the PR, which sub-item to name. Never To Deploy: an angle's work is method work, not a product change, and the release issue tracks the delivery.
5. **The coordinator reviews each angle PR, the bridge merges it; the consolidation is the overall review.** The coordinator reviews each angle PR as it comes, as a reviewer: it rejects false alarms with a reason in the thread, confirms whether each finding is blocking, resolves conflicts between angle branches, and approves at the head or requests changes. The bridge merges an approved angle PR into the release branch (merge commit, pinned to the head SHA) and closes its sub-item, only when the PR changes nothing but its report: one that carries any other file is not merged, and is told once per head, on the PR, that an angle fixes nothing (the stricter choice: a fix that rode an angle PR would reach the release branch with no ticket, no review of its own and no candidate built from it); an angle PR a person merged is found merged at the next tick and gets the same transitions, once (spec 09); a standing request for changes from another reviewer is handled as for any PR (`04-pr-review.md` §6): an App's, superseded by the coordinator's approval at the head, is dismissed right before the merge, a person's holds the PR. A blocking finding becomes an **urgent fix ticket**, created by the bridge from the merged report: in Ready, assigned to the release fixer `release.fix_assignee` (unassigned, taken by role, when the key is unset or unknown), labelled with the release label, it `blocks` the release issue, so there is no GO while it is open; its fix is a PR to the release branch, and that fix merged makes the next candidate (BR-ASDLC-022, `06-qa-report.md` rule 3). Once every angle PR of the candidate is merged, its consolidation item is served: the **overall review**. The coordinator reads every merged report together, confirms or rejects the non-blocking findings (the tickets the bridge files from the merged reports, unchanged, §6), checks that nothing falls between the angles, then tags the next candidate (§7). The consolidation item goes **Done** when a newer candidate is tagged, or when the release is published; the cycle's closure closes it otherwise (§11).
6. **Non-blocking findings become tickets logged for later, created by the bridge** from each merged report: one ticket per non-blocking finding, in `Triage`, labelled `qa-finding` and with the release label, normal priority, unassigned, related to the release issue (`06-qa-report.md` rule 4). It holds nothing: it is refined and scheduled like any ticket. There is no nits ticket and no `release.nits`. The agent never writes to the tracker.
    **Everything served to an agent carries a full contract** (BR-ASDLC-012): every finding's ticket, blocking or not, has a goal, non-goals, the finding under `## Acceptance criteria` (what was observed, where, and in what context, as the report gives it, and its proposed test), and `No new rule.` under `## Business rules`; no runtime exempts a ticket from the contract by its marker. Each is found again by its finding marker (candidate, angle, finding id), whatever became of it, so it is never filed twice. A shared nits ticket an older bridge opened is never written into; the closure archives it once resolved (§11).
7. **Every merged fix tags a new RC.** After angle PRs are merged, the next RC is tagged (by the coordinator through the cut workflow's `candidate` action, dispatched on the release branch, at the end of the overall review, §5, or by the bridge when the project's policy says so; the new tag ends the previous candidate's consolidation item), the gate runs again, and the configured policy says whether the angles review again: by default, **full QA on every RC** until `max_rc_passes` is reached; a project may choose "gate and coordinator only" for the following passes.
8. **The GO is computed.** All at the latest RC: gate green; every angle PR of this RC merged (or, for a later pass under the lighter policy, which offers no angle, every angle PR of the first candidate merged into the release branch; for a candidate with no QA angle, this condition does not apply); no open blocking finding (no open ticket `blocks` the release issue, nor carries its blocker marker without the relation); no resolved blocker whose fix is not in the candidate (a newer candidate that contains it frees it; the GO decision holds the condition, `fix_gaps` in `release status`, but the bridge does not read the fixes yet, so it holds no GO today); the RC is the release branch tip, modulo bookkeeping: the configured `bookkeeping_paths` (exact paths) and the reports of this RC's own angles (`release.record` rendered for this RC, one per configured angle), which its angle PRs commit after it by construction, so that the last allowed pass, which cuts no further RC, can reach a GO. A report of an earlier RC, and any other file after the RC (a fix, a code change), is a tip gap. Nobody gives the GO. The `human` policy is meant to add the owner's approval on the release issue to the computed conditions, but that approval is **not implemented**: the bridge does not read it (`.spl-asdlc/open-points.md` #3), so under `human` it never reaches a GO, and a person tags and publishes the release instead (§9, `09-requalification-and-human-gestures.md`). A person who tags the release and publishes it by hand does not give the bridge a GO: they take it on themselves, outside the computed conditions (§9).
9. **The bridge tags the release on GO and publishes it**: first the release note into the release issue (§12), so that no placeholder is left at publication (a note that cannot be built or written holds the GO, retried at the next tick); then the annotated release tag `release.release_tag` on the latest candidate's own commit, then the GitHub release of that tag, its notes the version's CHANGELOG section the cut prepared on the release branch, read at the candidate; both as the App. Each is read before it is written: a tag already on the candidate (a person's) is taken as done, a tag on another commit stops the GO, said at each tick, and a release already published is the publication's. A candidate whose CHANGELOG has no section for its version is not released: said at each tick, fail-closed. The bridge automates the GO and is not the only one able to do it: a person the tag rulesets let tag may tag the candidate and publish the release in GitHub instead (`git tag -a <release tag> <candidate's commit>`, `git push origin <release tag>`, `gh release create <release tag> --notes-file <the version's CHANGELOG section>`), taking the GO on themselves (`09-requalification-and-human-gestures.md`, BR-ASDLC-021); should the bridge reach the GO first, its tag is the same tag on the same commit, and the person publishes nothing twice: a release already published is the publication's. The bridge then publishes nothing more, closes the cycle from the published release as below, and its closure comment records who published the release. The published release is the signal, whoever made it: the `release-publish` workflow runs on it, verifies that the RC's gate was green, that the release tag's commit is the RC's, or differs from it only by the RC's own angle reports under `release.record` (a person who tagged the branch's tip after the last pass; a report of an earlier candidate is refused), and that the release was published by the bridge's App or by a human account (any other bot is no GO; the run says which in `go-published-by-kind` and its summary), runs the project's publication and deployment steps, merges the release branch back into `main` (never `main` into the release branch), deletes the branch, and fails if the merge-back or the guard was skipped. A merge back a person did by hand in GitHub is taken as done, never redone (spec 09).
10. **Escalation when the passes are exhausted.** If blockers remain after the last allowed RC pass, the bridge assigns the release issue to the owner with a hold label and a comment that lists the blockers. The hold label (`release.escalation_label`) is created first when the tracker lacks it. The hand-off is idempotent as a whole: the owner is assigned before the comment, the label is written whenever it is missing while the escalation holds, the comment carries a marker and is posted once; a failed label write never holds the comment back, and the next tick retries only what is missing. The owner may requalify a blocker (`09-requalification-and-human-gestures.md`), abandon the cycle, or allow one more pass by raising `release.max_rc_passes` in the configuration (a pass allowed in the issue itself is **not implemented**: the bridge reads only the configured count, `.spl-asdlc/open-points.md` #8).
11. **Closure is triggered by facts.** When the bridge sees the release published and the merge-back merged, it closes the cycle. The embarked tickets are the tickets linked to the PRs of the range, never the items the bridge linked to those PRs for their review (the angle sub-items and consolidation item of a PR round, `04-pr-review.md` §3), recognised as the PR pass recognises them (`01-ticket-contract.md` §7): by their marker, or by a parent that is another item linked to the same PR, whatever their description says. Such an item is not labelled with the release, is in neither the brief nor the note, and is **never judged**, even when it carries the release label (an earlier bridge labelled it) and whatever its status (the tracker may have moved it with its PR): it closes by its review, never by boxes, so the closure never sends it back; once resolved it is archived with the cycle, as below. Each embarked ticket in To Deploy or Post Deploy whose latest merged PR is in this release's range is judged (a ticket whose next PR merged after the cut is left to the release that ships it, spec 04 §10; every box ticked → **Done**; only `## Post deploy` boxes open → **Post Deploy**, with a **validation sub-task** created under it, unassigned, in Ready, **urgent**, since production is waiting on it (BR-ASDLC-017); otherwise → **In Progress**, **unassigned**, with the list of what remains); an embarked ticket In Progress or In Review shipped a PR that did not close it and is left to its next PR; each business rule cited by an embarked ticket is verified against the registry at the release tag, fail-closed: the rule's file `.spl-asdlc/business-rules/<ID>.md` must be there (`02-business-rules.md` §5; a cited rule with no file sends the ticket back to **In Progress**, unassigned too, an unreadable registry leaves it in its state); a ticket the closure sends back is never kept on its current assignee nor handed to someone named: rework is distributed by being pickable, and the agent system resumes it by role (BR-ASDLC-009); the bridge's own children of the release issue still open (angle sub-items, a consolidation item the publication did not end) are closed **Done**; the release issue is closed with the summary; the **record** (the merged angle reports) is now on `main`. **Once the release issue is closed, the bridge archives what the cycle resolved** (BR-ASDLC-019), so that a tracker that counts its open items against a limit (Linear's free plan) keeps room for the next cycle: the resolved children of the release issue (its angle sub-items, its consolidation item, any other child such as a gate fix), the shared nits ticket an older bridge opened, once resolved, the resolved PR review round items (angle sub-items and consolidation items, recognised by their bridge markers) of the embarked tickets, including one that carries the release label, and the embarked tickets the closure moved to **Done**; then the tickets with nothing to deploy (the no-deploy label, `04-pr-review.md` §10) whose latest merged PR is in this release's range and which their merge delivered (**Done**), with their resolved round items; the release issue goes last. It **never archives an open item**: a ticket in Post Deploy (and its validation sub-task) or In Progress, a finding in Triage, an open nits ticket stay; nor an item with an open sub-item, nor an item in a state the status table does not place, and the release issue waits while one of its children is open. An archived item stays searchable and restorable; one already archived is skipped, so a second tick writes nothing. A failed archive is reported and retried at the next tick (the release issue, archived last, keeps the cycle in view until then); it never blocks nor undoes the closure. A release issue closed by hand, without the closure, is not archived from, and a tracker without an open-item limit (Livela) archives nothing.
    A ticket in **Post Deploy** is never served itself: its validation sub-task is. The agent that takes it verifies the ticket's `## Post deploy` boxes in production, checks on the ticket the ones it can verify, and closes the sub-task; a check that needs a human, or is beyond it, is named in a comment and the sub-task is reassigned to the owner, who finishes. There is no verb: the bridge moves the ticket from Post Deploy to **Done** at the tick that finds every box of its `## Post deploy` section checked (the same Done gate as the closure's), and leaves it in Post Deploy while one box is open.
    Once the closure moved the release issue to Done, the cycle is over: `spl-asdlc release status` says that no cycle is in flight and which release closed the last one (`no cycle in flight: the last cycle closed with <release tag> (<release issue>)`; with `--json`, `{"in_flight": false, "closed_with": …, "release_item": …}`), and exits 0.
12. **The release note is part of the deliverable.** It announces every PR of the release's range, the release's own bookkeeping apart (merge backs of a release branch and their conflict resolutions, angle report PRs, `chore(release)` PRs): each ticket once, with its PRs, by its `## Release note` snippet (its Goal when it has none), a ticket with nothing to deploy included; and under **No linked ticket**, each PR no ticket describes, by its own `## Release note` section, or its title when it has none. The brief lists those PRs under "No linked ticket" too. The bridge writes the note into the release issue's `## Release note` section in place of the fresh issue's placeholder, at the candidate's brief and again at the GO before the release is published (§9), so that a GO a person makes in GitHub finds it there as well; the closure writes it once more if the range changed, and sends it through the configured channels. A failed send is a failed closure step, retried, never dropped. With no channel configured for the release note, there is nothing to send: the release item carries the note, the closure says so once and goes on (`07-the-bridge.md`, "What it sends").
13. **Abandoning a cycle** keeps the RC tags, merges the release branch back into `main` so that merged fixes are not lost, cancels the release issue, turns each remaining blocker into a ticket, and the next cut starts a new cycle from `main`.
14. **A release the bridge did not open is not its cycle.** A version already published with no release issue of the bridge (a release made before the bridge took the product over) is left alone: no issue, no closure, no note. The bridge's first cycle on a product is the first one cut after it took over.

## The brief

Posted by the bridge on the release issue once per RC, once that RC's gate is green (§3): the candidate (tag, commit, class), the range, the embarked tickets with their acceptance criteria (each ticket is found by commit → PR → linked ticket, never by text; the bridge's own review items linked to a PR are not tickets, §11), the business rules touched (the rule files of `.spl-asdlc/business-rules/` the range changes), the link to the evidence pack, the angles and their sub-items. A range, PR, link or evidence pack that cannot be read makes the brief fail; it is never guessed or left empty, and the angle sub-items wait with it, so that no agent starts without its brief.

## The range and the first release

A candidate's range is Git's: the commits of the candidate that the highest published release below its version does not contain. The version and the notes `release prepare` writes (§1), the release class the cut computes, the gate's evidence pack, the embarked tickets, the brief and the closure (§11) all read this one range.

**A product's first release needs no base tagged by hand.** With no published release below the candidate, the range is the candidate's whole history, measured from the repository's root, and each step says so:

- the cut computes the class on every file of the history and records the base `root` in the tag (`Release-Class-Base: root`), so a first release whose history holds a reviewed path is `sensible` (the reviewed paths are the union of the `paths` of `[[review.angles]]` in the configuration at the candidate: with none, no path is reviewed apart and the class is `routine`; a configuration whose angles' paths cannot be read makes it `sensible`);
- the gate does not fail: its `last-tag` output is empty, and its log, `run.json` and `results/suites.json` (`lastReleaseTag` and `from_tag` null) and its report say the candidate is measured from the repository's root; the PR guards it re-runs get the empty tree as `BASE_SHA`;
- the brief reads "Diff since the repository's root: first release", and lists every path at the candidate;
- `release prepare` reads the whole history and bumps the version from `0.0.0` (a `feat` makes it `0.1.0`), unless `--version` forces the first one; its CHANGELOG heading has no compare link;
- `doctor` reports the release base it finds, or that the first candidate will be measured from the root.

## Configuration (per project)

- Release shape: candidate tag pattern, final tag pattern, the record file, the version files besides Rust's own, the CHANGELOG sections.
- Release angles with assignee hints, or `angles = []` for a release with no QA angle (§3); the tracker participant who receives the consolidation item (`release.coordinator_assignee`, optional); `max_rc_passes` (default 2); the policy for later passes (`full` | `gate-and-coordinator`); GO policy (`computed` | `human`); the release fixer who receives the urgent fix tickets (`release.fix_assignee`, optional).
- Publication and deployment steps (inputs of `release-publish`); the binary channel of the cut (`spl-asdlc-version`).
- Notification channels for the release note.

**One product, one version.** A release has one version, one tag, one CHANGELOG section and one publication. A product built for several platforms from that version (desktop, mobile, web, server binaries) is still one product: its publication job builds and deploys every target, and a target that reaches production later (a store's review) is verified through the ticket's `## Post deploy` section. Deliverables versioned and released independently of each other (multi-component products) are not supported: such a product is set up as one repository per deliverable, or waits for that support.
