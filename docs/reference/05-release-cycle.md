# 05 — The release cycle

Exhaustive, on the whole project, in release candidates. The bridge coordinates; agents and humans do the QA on branches; the GO is computed.

Every project has the cycle: a configuration without a `[release]` section is refused (`08-configuration.md` rule 11). What is optional is its QA: a cycle with `release.angles = []` has no QA angle, and its GO rests on the release CI (§3). A merged ticket waits To Deploy for the next release; only a ticket with nothing to deploy goes straight to Done at its merge (`docs/method.md`, "Merge").

## Invariants

1. **A human opens a cycle.** The cut is a `workflow_dispatch` of the `release-cut` workflow (`open`): it creates the release branch `release/<YYYY-MM-DD-HH-MM>-utc` from `main`, refuses when a release branch is already in flight, **prepares the release** on it with `spl-asdlc release prepare` (the published binary of the channel the caller names, its checksum verified), commits `chore(release): v<X.Y.Z>` and pushes the branch and its first RC tag, annotated with the release class, in one atomic push. The preparation follows the git graph, never dates: the version is computed from the commits of `<last release tag>..HEAD` (Conventional Commits; a breaking change, `!` or `BREAKING CHANGE`, bumps the major from 1.0, a `feat` the minor, anything else the CHANGELOG lists the patch; before 1.0 a breaking change or a `feat` bumps the minor and the rest the patch; with no earlier release the whole history is read and the version bumped from `0.0.0`; `--version` forces one), written into the version files (Rust's `Cargo.toml` and `Cargo.lock` natively, any other through `release.version_files`), and the CHANGELOG gets the version's section in the Conventional Commits CHANGELOG format, as release-please writes it (the heading with its compare link, then `### ⚠ BREAKING CHANGES` and one section per type of `release.changelog_sections`, each entry with its PR and commit links), which is also the release notes; with `release.changelog_dir`, those notes are also written as the version's own file, `<dir>/<X.Y.Z>.md` (`08-configuration.md`). No PR writes the CHANGELOG nor that folder: only the cut does, once per version, but for the unified release note, which rewrites the version's own section and file on the release branch (§12). A range with nothing to release (no Conventional Commit of a listed type, no breaking change) is refused, and nothing is created. A commit merged into `main` while the previous cycle was open, which only the merge-back brought into this range, is in this release's notes by construction. **No job waits for another workflow's run**, so one runner is enough. Every later candidate is a `candidate` dispatched on the release branch (`--ref release/<stamp>-utc`), never on `main`, which tags rc.N+1 on its tip: the version is already committed there. Nothing else happens in CI.
2. **The release issue follows at the next tick.** The bridge sees the new branch and tag, creates the **release issue** (title: product and the version its candidate tag names; assigned to the owner `owner.tracker_user`, who follows the cycle and takes over any step by hand, so that no agent that takes unassigned items takes it, or unassigned when the tracker does not know that person, which `doctor` reports; an issue already open is never reassigned; **In Progress** while its cycle runs, until the closure moves it to Done (§11), and one found in Ready or Backlog is moved In Progress at the next tick, its assignee kept), records the candidate on it and labels every embarked ticket `release/<product>-v<version>` whatever its state but Canceled (every merged PR is deployable, `04-pr-review.md` §10); the bridge's own review items linked to the same PRs are not embarked tickets (§11), nor is a ticket with nothing to deploy (the no-deploy label, `04-pr-review.md` §10), which its merge delivered. Nothing starts before the issue exists, so a tag without an issue is harmless. The angle sub-items and the brief wait for the gate (§3).
3. **The gate judges the frozen tag.** The `release-gate` workflow runs the project's suites on the RC tag, writes `results/suites.json`, uploads the evidence pack, and fails closed on any skipped or absent suite. QA does not start on a red gate. **Once the candidate's own gate run is green**, and never before, the bridge creates one **angle sub-item** per configured release angle and one **consolidation item** for that candidate (each angle sub-item assigned to its angle's `assignee`, the consolidation item to the coordinator named by `release.coordinator_assignee`, an agent the tracker serves; an unset or unknown participant leaves the item unassigned, and completing the round never reassigns an existing item; an angle sub-item is then reassigned by its flow only, §4), the consolidation item **served only once every angle report of the candidate is merged** (BR-ASDLC-020), then posts the **brief**, which links the gate run and its evidence pack. On a tracker that holds **implementation blocks** (a block freed once its blocker is To Deploy, which a Livela store may offer), the consolidation item is created **Ready** and blocked by every angle sub-item of the candidate through its implementation; on any other tracker (Linear included) it is created in **Backlog**, and the bridge moves it to **Ready** once every angle sub-item offered to the candidate is To Deploy or later (and back to Backlog, from Ready only, should that stop holding). A block of the release kind an older bridge laid from an angle sub-item would hold the consolidation item until the release: the bridge removes it, and only it: an implementation block that the tracker also lists among the item's plain blocks (Livela keeps it as a block with a kind) is kept, never removed and laid again at the next pass. The relations and the status are written right after the items and before the brief; one already right is not written again, and an open consolidation item missing one gets it at the next tick. A relation that cannot be read or written is reported and **holds the brief**, fail-closed: the items stay, but the brief, which is what starts the angles' work, is not posted that tick; the next tick lays the missing relations and only then posts the brief, once. So no angle starts while its consolidation item could be served before it. A red, pending or unreadable gate opens no angle and no brief; each new RC waits for its own gate in the same way.
    **A release may have no QA angle.** A project that writes `release.angles = []` (`08-configuration.md`) runs the cycle without a QA round: the release item, its candidate record, the embarked labels, the gate and its gate-fix tickets, the GO's tag and release, the publication and the closure are as above; once the candidate's gate is green the bridge opens no angle sub-item and no consolidation item and posts the brief alone, which says that no QA angle is configured. The candidate's record says so too, with the marker `spl-asdlc:no-qa-angle candidate=<tag>`: angles configured later apply from the next candidate, never to one recorded with none. The gate stays: it is the release's minimum.
    **A tracker with milestones groups each candidate's QA** (BR-ASDLC-038): on a tracker that has them (Livela, once its store creates milestones under a release item), the bridge creates one **milestone** per candidate under the release issue, named after the candidate's tag, the first time the candidate has a QA item to create, and creates that candidate's angle sub-items and consolidation item in it rather than directly under the release issue. The milestone is the tracker's grouping, its status derived from its children: the bridge never sets it, and reads the items in it as the release issue's own children everywhere else (the GO, the closure, `release status`). A milestone that cannot be read or created creates no QA item, and the next tick retries. A tracker without milestones (Linear) keeps the items directly under the release issue. **PR reviews stay in GitHub**: the bridge creates no review item in the tracker for them, and the GitHub sync mirrors each PR's reviews, read-only, on the tickets linked to it (`livela-contract.md`, "GitHub → item sync").
    **A red gate is never a silence** (BR-ASDLC-016): an **implementer** fixes it on the release branch, from a **gate-fix ticket** the bridge opens. Once the candidate's gate run concluded red and its one automatic rerun of runner aborts and known flakes has settled (the run's latest attempt is a rerun that completed red, or the rerun workflow `release.gate_rerun_workflow` ran for its first attempt and every such run completed; until then the bridge waits, since it cannot read whether a rerun will come. The runs of the rerun workflow for a gate run are its `workflow_run` runs created from the gate run's completion until `release.gate_rerun_wait_minutes` after it, matched by time and not by commit: GitHub runs a `workflow_run` workflow on the default branch's head, never on the commit of the run that triggered it, and a listed run does not name that run), **or no run of the rerun workflow showed up within `release.gate_rerun_wait_minutes` (default 30) of the gate run's completion** (the rerun workflow may be absent or broken: the ticket then says no rerun was seen; a rerun run that showed up and is still running keeps the wait, whatever the bound), the bridge opens **one gate-fix ticket per candidate**, found again by its marker `spl-asdlc:gate-fix candidate=<tag>` among the release issue's children whatever its state, never twice: a child of the release issue, labelled `release/<product>-v<version>`, assigned to the release fixer `release.fix_assignee` (**unassigned** when the key is unset or the tracker does not know it, so that an implementer takes it by role), in **Ready**, **urgent**. Its contract is complete: the goal is the gate green on the release branch; the failing suites are read from `results/suites.json` of the evidence pack, with the link to the gate run (an evidence pack that cannot be read still opens the ticket, which says the failing suites are unknown and links the run); the non-goals are no new feature and no change beyond what the failure needs; the acceptance is the failing suites passing on the release branch (the listed suites, or the suites that failed in the gate run when they are unknown), an ordinary box the implementer ticks once it verified it on that branch, as any criterion; `No new rule.` under `## Business rules`. The fix is a PR whose base is the release branch (`docs/agents/process.md`, "Implement a ticket" step 2); the next RC is cut by the coordinator, or by the bridge when `auto_candidate = true` (§7). The ticket follows the flow of any ticket: **To Deploy** at its fix's merge (`04-pr-review.md` §10), **Done** at the release's closure (§11). The gate of the next candidate is the verification: when it is red too, the bridge opens a new gate-fix ticket for that candidate, as above. When the gate of the newest candidate is green, the bridge closes every gate-fix ticket of the cycle opened for it or an earlier candidate that never reached a merge, still in Triage, Backlog, Ready or In Progress (a rerun made the gate green, say): **Done**, with a comment naming the green candidate. Any other is left alone: In Review (its PR is being judged), past the merge (the closure judges it, §11) or already resolved. A red gate older than `stagnation_hours` raises the stagnation notice as well, once.
    **Each item carries its protocol** (BR-ASDLC-015), as in a PR review (`04-pr-review.md` §3): beside its contract and what closes it in the bridge's terms, an angle sub-item embeds `docs/agents/review-release.md`, the angle's file `docs/agents/angles/<angle>.md` (or, for an angle of the project's own, a line saying the method has no notes for it) and the schema and rules of the angle report (`06-qa-report.md`); the consolidation item embeds `docs/agents/consolidate.md` and the same schema and rules. The project's angle notes are linked, never embedded. The texts are those of the version of spl-asdlc the project is pinned on, the ref of its workflow callers at the candidate's tag (`08-configuration.md`, "Angles", BR-ASDLC-032), but for the report's schema and rules, which are the bridge's own; texts that cannot be read there create no item, and the bridge says so on the release issue instead of copying other texts. An item keeps its texts while open, since an item found again by its marker is never rewritten (it is found by its exact title among the release issue's children as well, so that an edited marker never makes the bridge create it twice, REQ-REL-048); a later candidate's items carry the texts its own tag pins. An angle sub-item goes To Deploy when the bridge merges its angle PR, and Done when a newer candidate is tagged or the release is published (§4, §5); the consolidation item goes Done when the bridge merges its verdict, or else at the closure; a newer candidate cancels any of them still open before that (§5, §11, BR-ASDLC-038).
4. **Each angle works on its own branch.** The reviewer of an angle cuts `qa/<candidate>/<angle>` from the release branch, reviews the whole project from its angle (with the brief, the evidence pack, the tag annotation and the diff as orientation), classifies each finding as blocking or not and documents it, fixes nothing, commits its **angle report** (`06-qa-report.md`, mandatory even when nothing was found) and nothing else, and opens a PR to the release branch whose body names its sub-item. The angle sub-item follows the normal flow of a work item (BR-ASDLC-020): **In Progress** when the angle's work starts (the bridge, when its angle PR is opened; a draft angle PR is out of the flow, as any draft, and drives nothing), **In Review** when its agent moves it there once its PR is opened (it is a ticket whose code is its report: In Review keeps it from being served again while the bridge checks the PR, ASDLC-WMTX), or when that PR's required checks are green, back **In Progress** when a configured coordinator requests changes on it at its head, or when what holds the PR is the angle's to mend (a required check red, its report missing or invalid, a change besides the report), **To Deploy** when the bridge merges it, or finds it merged by a person (spec 09), and **Done** when a newer candidate is tagged or the release is published. In Review is the bridge's step, served to nobody: it keeps the item's assignee, and nobody approves an angle PR. The write that sends it back In Progress assigns it to its angle's `assignee`, or to nobody when none is configured or the tracker does not know it (taken by role); To Deploy and Done leave the assignee as it is. A status and assignee already right are not written again. An angle PR that names no sub-item is neither followed nor merged, and is told once per head, on the PR, which sub-item to name. To Deploy, as a ticket at its merge, is what frees the consolidation item (§3).
5. **The bridge merges each angle PR; the coordinator's verdict is the consolidation.** The bridge merges an angle PR into the release branch (merge commit, pinned to the head SHA) once it names its sub-item, carries a valid report (`06-qa-report.md`, rules 1 and 2) and nothing else, its required checks are green and it is up to date with the release branch: **no approval is asked**. One that carries any other file is not merged, and is told once per head, on the PR, that an angle fixes nothing (the stricter choice: a fix that rode an angle PR would reach the release branch with no ticket, no review of its own and no candidate built from it). A coordinator may still read an angle PR and request changes at its head: that request holds the merge and sends the sub-item back to its angle (§4); any other standing request for changes, a person's or an App's, holds it too, as nothing supersedes it. An angle PR a person merged is found merged at the next tick and gets the same transitions, once (spec 09). A merged report files **no ticket on its own**. Once every angle report of the candidate is merged, its consolidation item is served (§3): the coordinator reads every merged report together, judges each finding once, accepted (blocking or not) or rejected with its reason, checks that nothing falls between the angles, and commits its **verdict** (`06-qa-report.md`, "The verdict"), `go` or `hold`, from the branch `qa/<candidate>/consolidation` in a PR to the release branch that names the consolidation item. The bridge merges the verdict PR (merge commit) when the verdict is valid against the merged reports and the PR carries nothing else, every angle PR of the candidate is merged, its author is one of `release.coordinators` or one of them approved it at its head, its required checks are green and it is up to date; what else keeps it from the merge is said once per head, on the PR (rule V7QD). At its merge the bridge files the **accepted** findings only, each once: an accepted blocking finding becomes an **urgent fix ticket**, in Ready, assigned to the release fixer `release.fix_assignee` (unassigned, taken by role, when the key is unset or unknown), labelled with the release label, and it `blocks` the release issue, so there is no GO while it is open; its fix is a PR to the release branch, and that fix merged makes the next candidate (BR-ASDLC-022, `06-qa-report.md` rule 3). Once its fix is merged (the ticket To Deploy or later), a candidate that contains that merge frees the GO of it (§8): the ticket itself reaches Done only at the closure, which follows the publication, so waiting for Done would never let the release go. The bridge's comment at the fix's merge says so. A rejected finding files nothing: its reason stays in the verdict. The consolidation item then goes **Done**. It is a ticket whose code is the verdict: its coordinator moves it **In Review** once the verdict PR is opened, and the bridge moves it back **In Progress** when what holds that PR is the coordinator's to mend (the PR names no item, carries another change or an invalid verdict, or a required check is red) or when no verdict PR is open (ASDLC-WMTX). A newer candidate redoes every review: in the pass that first sees it tagged, every angle sub-item of an older candidate at To Deploy goes **Done**, and every QA item of it still open before that, its angle sub-items and its consolidation item, goes **Canceled** (BR-ASDLC-038); the cycle's closure closes what is left otherwise (§11).
6. **Non-blocking findings become tickets logged for later, created by the bridge** from the merged verdict: one ticket per finding the verdict accepts as non-blocking, in `Triage`, labelled `qa-finding` and with the release label, normal priority, unassigned, related to the release issue (`06-qa-report.md` rule 4). It holds nothing: it is refined and scheduled like any ticket. There is no nits ticket and no `release.nits`. The agent never writes to the tracker.
    **Everything served to an agent carries a full contract** (BR-ASDLC-012): every finding's ticket, blocking or not, has a goal, non-goals, the finding under `## Acceptance criteria` (what was observed, where, and in what context, as the report gives it, and its proposed test), and `No new rule.` under `## Business rules`; no runtime exempts a ticket from the contract by its marker. Each is found again by its finding marker (candidate, angle, finding id), whatever became of it, so it is never filed twice. A shared nits ticket an older bridge opened is never written into; the closure archives it once resolved (§11).
7. **Every merged fix tags a new RC.** After a `hold` verdict and its fixes, the next RC is tagged (by the coordinator through the cut workflow's `candidate` action, dispatched on the release branch, once the verdict is merged, §5, or by the bridge when `release.auto_candidate = true`; the new tag ends the previous candidate's QA items), the gate runs again, and the configured policy says whether the angles review again: by default, **full QA on every RC whose gate is green**, whatever its RC number; a project may choose "gate and coordinator only" after the first candidate. A red candidate opens no QA round and therefore consumes no QA pass. `max_rc_passes` controls escalation (§10), not which candidates are reviewed. **When the bridge cuts** (`release.auto_candidate = true`, rule C8WN): at a tick that merged nothing and computed no GO, it dispatches `release.cut_workflow` with `action=candidate` on the release branch when all of these hold: the branch moved past the latest candidate with a file that is not bookkeeping (§8: the configured `bookkeeping_paths`, this candidate's own angle reports and verdict, and with a note writer the version's release note files); no gate-fix ticket of the release (§3) and no blocking finding's fix ticket of the release (§5: the release label and the blocker marker naming the release issue) is still before To Deploy (Triage, Backlog, Ready, In Progress, In Review, or an open state the status table does not place); the latest candidate is not already reaching its GO (the GO computed, or the release tag already there); and the latest candidate is not the last allowed pass (`max_rc_passes`), where the escalation hands the cycle to the owner instead (§10). It dispatches once per branch head: the dispatch first, then a comment on the release issue carrying the marker `spl-asdlc:auto-candidate branch=<branch> head=<sha>`; a head whose marker is there is never dispatched again, and a dispatch that failed writes no marker and is retried at the next tick (a cut run that failed after its dispatch is not: a person dispatches the cut again, or the next fix moves the head). A dry run prints the dispatch it would do and writes nothing. Without `auto_candidate`, the bridge dispatches nothing: `release status` says that the branch moved past the candidate and that a cut of the next candidate is due, and the coordinator, as its protocol says, or a person cuts it (`spl-asdlc release cut`).
8. **The GO is computed.** All at the latest RC: gate green; every angle PR of this RC merged (or, for a later pass under the lighter policy, which offers no angle, every angle PR of the first candidate merged into the release branch; for a candidate with no QA angle, this condition does not apply); the coordinator's verdict on this RC merged and `go` (rule V7QD; not asked of a candidate with no QA angle, nor of a later pass under the lighter policy); no open blocking finding (no open ticket `blocks` the release issue, nor carries its blocker marker without the relation); a blocking finding of the release (the release label and the blocker marker naming the release issue) at To Deploy or later is not open once its fix is in the candidate: every PR the bridge recorded as merged on it (the `merged_pr:` lines of its own comments) was merged by a commit the candidate contains (REQ-REL-059); one whose fix is not in the candidate is a **fix gap** (`fix_gaps` in `release status`), which a newer candidate that contains it frees; fail-closed, a fix with no recorded merged PR, a recorded PR not merged, or a PR or an ancestry that cannot be read is a fix gap too, and any other open blocker, a finding before To Deploy included, is open; the RC is the release branch tip, modulo bookkeeping: the configured `bookkeeping_paths` (exact paths) and the reports of this RC's own angles and its verdict (`release.record` rendered for this RC, one per configured angle and one for the key `consolidation`), which its angle PRs and its verdict PR commit after it by construction, so that the last allowed pass, which cuts no further RC, can reach a GO. A report of an earlier RC, and any other file after the RC (a fix, a code change), is a tip gap. Nobody gives the GO. The `human` policy is meant to add the owner's approval on the release issue to the computed conditions, but that approval is **not implemented**: the bridge does not read it (`.spl-asdlc/open-points.md` #3), so under `human` it never reaches a GO, and a person tags and publishes the release instead (§9, `09-requalification-and-human-gestures.md`). A person who tags the release and publishes it by hand does not give the bridge a GO: they take it on themselves, outside the computed conditions (§9). A person may hold the GO instead: the hold label (`release.hold_label`, default `hold`) on the release issue keeps the GO false whatever the other conditions say, so the bridge neither tags nor publishes the release, while it keeps merging PRs and moving tickets; `release status` names the label and the issue among its reasons, and removing the label lets the GO be computed again at the next tick.
9. **The bridge tags the release on GO and publishes it**: first the release note into the release issue (§12), so that no placeholder is left at publication (a note that cannot be built or written holds the GO, retried at the next tick); then the annotated release tag `release.release_tag` on the latest candidate's own commit, then the GitHub release of that tag, its notes the version's CHANGELOG section the cut prepared on the release branch, read at the candidate; both as the App. Each is read before it is written: a tag already on the candidate (a person's) is taken as done, a tag on another commit stops the GO, said at each tick, and a release already published is the publication's. A candidate whose CHANGELOG has no section for its version is not released: said at each tick, fail-closed. The bridge automates the GO and is not the only one able to do it: a person the tag rulesets let tag may tag the candidate and publish the release in GitHub instead (`git tag -a <release tag> <candidate's commit>`, `git push origin <release tag>`, `gh release create <release tag> --notes-file <the version's CHANGELOG section>`), taking the GO on themselves (`09-requalification-and-human-gestures.md`, BR-ASDLC-021); should the bridge reach the GO first, its tag is the same tag on the same commit, and the person publishes nothing twice: a release already published is the publication's. The bridge then publishes nothing more, closes the cycle from the published release as below, and its closure comment records who published the release. The published release is the signal, whoever made it: the `release-publish` workflow runs on it, verifies that the RC's gate was green (the newest push run on the RC of `release.gate_workflow`, which it reads from the configuration at the release's commit unless its caller passes `gate-workflow`, `08-configuration.md`), that the release tag's commit is the RC's, or differs from it only by the RC's own angle reports under `release.record` (a person who tagged the branch's tip after the last pass; a report of an earlier candidate is refused), and that the release was published by the bridge's App or by a human account (any other bot is no GO; the run says which in `go-published-by-kind` and its summary), runs the project's publication and deployment steps, merges the release branch back into `main` (never `main` into the release branch), deletes the branch, and fails if the merge-back or the guard was skipped. A merge back a person did by hand in GitHub is taken as done, never redone (spec 09).
    **A release whose publication failed before deploying is retracted.** While the closure waits for the merge back, the bridge reads the release's publication run: the newest run of `release.publish_workflow` (default `release-publish.yml`) on the `release` event at the release tag's commit, and the jobs of its latest attempt. The project's publication and deployment jobs `needs` the `verify` call, so a red verification means nothing was deployed. The bridge retracts the release only when the run completed red, a `verify` job of `asdlc-release-publish.yml` (a job named `<caller job> / verify`) concluded `failure`, `cancelled` or `timed_out`, and every other job but `closing-guard` was skipped (no job of the project's ran, no merge back ran: the merge back is the job named `<caller job> / merge back into main branch`, formerly `<caller job> / merge-back`, or `<caller job> / close` from a workflow tag up to 1.9.1, all three still read, so a run whose two calls pin different tags is judged the same), or when the run failed without starting any job (a workflow GitHub could not start); and no dispatch of the workflow (a resume, a replay) came after it. It then comments on the release issue, once (why, the run's link, that the next candidate takes the release tag; marker `spl-asdlc:retracted tag=<release tag> sha=<commit>`), and only then deletes the GitHub release and the release tag, as the App, which the tag rulesets let bypass them; each is read before it is deleted, so a second tick finds nothing to retract, and a deletion that failed is retried at the next tick. A run still running, a publication that succeeded, one whose deploy or merge back ran (the replay path above), and a run whose jobs cannot be read are never retracted; the last is said at each tick. The retracted candidate gets no second GO (`release status` names the retraction); the fix is a PR to the release branch, the next candidate's GO tags and publishes the same version, and a release tag a failed deletion left on the retracted commit is deleted first. `spl-asdlc release retract <release tag>` does the same by hand, with the same refusals, and refuses as well when no publication run is found or it cannot be read: there is no flag to override it (a person deletes the release and the tag in GitHub instead, `09-requalification-and-human-gestures.md`).
    **A release whose merge back is blocked gets a fix ticket, and the bridge lands it** (ASDLC-PQ5J, rules M5E7, K8FU, 3P4R). While the closure waits for the merge back, once the publication run concluded with its merge back job red (`failure`, `timed_out` or `cancelled`) and the release tag is still not in `main`, the bridge reads the open merge-back PR of the release branch: `DIRTY` (a real conflict), a required check of `main` red on its head, or its required checks green and the PR still `BLOCKED` or `BEHIND` (the App refused by the ruleset). A PR whose checks still run says nothing yet. The bridge says the cause once on the release issue (marker `spl-asdlc:merge-back-blocked tag=<release tag>`), then opens one fix ticket « Make the merge back green — <release tag> » under it, assigned to `release.fix_assignee`, in Ready, urgent, found again by its marker `spl-asdlc:merge-back-fix tag=<release tag>`: a later tick on the same block opens no second one. Its contract is the recipe: cut `chore/merge-back-<stamp>` from the release branch's tip, merge `main` into it, commit the fix on top, and open its PR into `main`, titled as a Conventional Commit naming the ticket. It never brings `main` into `release/**`. While that ticket exists, the bridge merges a ready `chore/merge-back-*` PR of the repository into `main` as a merge commit, never a squash, pinned to its head. It does so once the PR's rollup is green with `main`'s required checks (`required-check` and the title check), and only when its branch contains the release branch's tip; otherwise it says once per head on the PR why it does not merge it. Once the release tag is in `main` and the release branch is still there, the bridge dispatches `release.publish_workflow` on the release branch with `replay: true`, once per release (marker `spl-asdlc:merge-back-replay tag=<release tag>`), unless a dispatch on that branch is still running. The replay deletes the branch and publishes nothing, and the closure goes on (§11), closing the fix ticket Done. A person may do any of these steps by hand (the manual recipe of « Release close », `docs/setup/repository.md`): the bridge takes the result as done, and the closure closes the fix ticket whatever its boxes say. A replay the bridge dispatched that fails is not dispatched again: a person replays.
10. **Escalation when the passes are exhausted.** If blockers remain after the last allowed RC pass, the bridge assigns the release issue to the owner with the escalation label and a comment that lists the blockers. The escalation label (`release.escalation_label`) is created first when the tracker lacks it. The hand-off is idempotent as a whole: the owner is assigned before the comment, the label is written whenever it is missing while the escalation holds, the comment carries a marker and is posted once; a failed label write never holds the comment back, and the next tick retries only what is missing. The owner may requalify a blocker (`09-requalification-and-human-gestures.md`), abandon the cycle, or allow one more pass by raising `release.max_rc_passes` in the configuration (a pass allowed in the issue itself is **not implemented**: the bridge reads only the configured count, `.spl-asdlc/open-points.md` #8).
11. **Closure is triggered by facts.** When the bridge sees the release published and the merge-back merged, it closes the cycle. A closure that has not ended when the next cycle is cut (the release note's channel failing, say) goes on at each tick beside the next cycle, whose release branch it does not wait for, until the release issue is Done; from then on the bridge writes nothing to that issue but what its archiving left. The embarked tickets are the tickets linked to the PRs of the range, never the items the bridge linked to those PRs for their review (the angle sub-items and consolidation item of a PR round, `04-pr-review.md` §3), recognised as the PR pass recognises them (`01-ticket-contract.md` §7): by their marker, or by a parent that is another item linked to the same PR, whatever their description says. Such an item is not labelled with the release, is in neither the brief nor the note, and is **never judged**, even when it carries the release label (an earlier bridge labelled it) and whatever its status (the tracker may have moved it with its PR): it closes by its review, never by boxes, so the closure never sends it back; once resolved it is archived with the cycle, as below. Each embarked ticket in To Deploy or Post Deploy whose latest merged PR is in this release's range is judged (a ticket whose next PR merged after the cut is left to the release that ships it, spec 04 §10; every box ticked → **Done**; only `## Post deploy` boxes open → **Post Deploy**, its status alone: no sub-task, no label, its assignee kept (BR-ASDLC-003); otherwise → **In Progress**, **unassigned**, with the list of what remains: every open box in full, under the ticket and then under each duplicate merged into it, by its id and title; how to reconcile a duplicate's boxes, which the closure counts until they are checked on the duplicate (rule W4KD); and what comes next (rule Q9TM)); an embarked ticket In Progress or In Review shipped a PR that did not close it and is left to its next PR; each business rule cited by an embarked ticket is verified against the registry at the release tag, fail-closed: the rule's file `.spl-asdlc/business-rules/<ID>.md` must be there (`02-business-rules.md` §5; a cited rule with no file sends the ticket back to **In Progress**, unassigned too, an unreadable registry leaves it in its state); a ticket the closure sends back is never kept on its current assignee nor handed to someone named: rework is distributed by being pickable, and the agent system resumes it by role (BR-ASDLC-009); the bridge's own children of the release issue still open (angle sub-items, a consolidation item the publication did not end) are closed **Done**; the release issue is closed with the summary; the **record** (the merged angle reports) is now on `main`. **Once the release issue is closed, the bridge archives what the cycle resolved** (BR-ASDLC-019), so that a tracker that counts its open items against a limit (Linear's free plan) keeps room for the next cycle: the resolved children of the release issue (its angle sub-items, its consolidation item, any other child such as a gate fix), the shared nits ticket an older bridge opened, once resolved, the resolved PR review round items (angle sub-items and consolidation items, recognised by their bridge markers) of the embarked tickets, including one that carries the release label, and the embarked tickets the closure moved to **Done**; then the tickets with nothing to deploy (the no-deploy label, `04-pr-review.md` §10) whose latest merged PR is in this release's range and which their merge delivered (**Done**), with their resolved round items; the release issue goes last. It **never archives an open item**: a ticket in Post Deploy or In Progress, a finding in Triage, an open nits ticket stay; nor an item with an open sub-item, nor an item in a state the status table does not place, and the release issue waits while one of its children is open. An archived item stays searchable and restorable; one already archived is skipped, so a second tick writes nothing. A failed archive is reported and retried at the next tick (the release issue, archived last, keeps the cycle in view until then); it never blocks nor undoes the closure. A release issue closed by hand, without the closure, is not archived from, and a tracker without an open-item limit (Livela) archives nothing.
    A ticket in **Post Deploy** is its own validation (BR-ASDLC-003): it is never served to an implementer, and no other item is created for it. An agent takes it first, verifies in production the `## Post deploy` boxes it can and checks them with their proof; when boxes remain that need a human, it assigns the same ticket to the owner with a comment that names them (`docs/agents/process.md`, "Validate a ticket in Post Deploy"). It carries no escalation label: validation is an action, not a PM decision. There is no verb: at each tick the bridge reads every item in Post Deploy and moves to **Done** each ticket whose `## Post deploy` boxes are all checked (the same Done gate as the closure's), whatever its labels, and leaves it in Post Deploy while one box is open (BR-ASDLC-002).
    Earlier versions created a validation sub-task under the ticket (marker `spl-asdlc:post-deploy-validation parent=<key>`) and labelled the ticket `post-deploy-validation/<product>`. The same pass cancels each such sub-task still open in Post Deploy, whatever key its marker names, once, after a comment that sends its reader to the ticket; and takes the label off a ticket it moves to Done (BR-ASDLC-017).
    Once the closure moved the release issue to Done, the cycle is over: `spl-asdlc release status` says that no cycle is in flight and which release closed the last one (`no cycle in flight: the last cycle closed with <release tag> (<release issue>)`; with `--json`, `{"in_flight": false, "closed_with": …, "release_item": …}`), and exits 0.
12. **The release note is part of the deliverable.** It announces every PR of the release's range, the release's own bookkeeping apart (merge backs of a release branch and their conflict resolutions, angle report PRs, `chore(release)` PRs that no ticket describes: one that describes a ticket embarks it like any other PR): each ticket once, with its PRs, by its `## Release note` snippet (its Goal when it has none), a ticket with nothing to deploy included; and under **No linked ticket**, each PR no ticket describes, by its own `## Release note` section, or its title when it has none. The brief lists those PRs under "No linked ticket" too. The bridge writes the note into the release issue's `## Release note` section in place of the fresh issue's placeholder, at the candidate's brief and again at the GO before the release is published (§9), so that a GO a person makes in GitHub finds it there as well; the closure writes it once more if the range changed. Each write happens only when the note differs from what the issue holds, the tracker's Markdown reformatting (bullets, indentation, list spacing) ignored; the block's end marker is a paragraph of its own, after a blank line, and an older issue whose marker the tracker indented into the last bullet is still found and rewritten. The closure sends the note through the configured channels. A failed send is a failed closure step, retried, never dropped. With no channel configured for the release note, there is nothing to send: the release item carries the note, the closure says so once and goes on (`07-the-bridge.md`, "What it sends").

    **The unified release note** is optional (ASDLC-4TQN). With `release.note_writer`, the bridge creates under the release issue, in the pass that first sees the release's first candidate, a task **« Write the unified release note of <X.Y.Z> »** (marker `spl-asdlc:release-note version=<X.Y.Z> step=write`), Ready, assigned to the writer (unassigned when the tracker does not know it): the writer rewrites the notes the cut prepared into one digestible note, tickets about the same thing merged into one entry, written for the user, and commits it on the release branch in the version's CHANGELOG section and, with `release.changelog_dir`, its `<dir>/<X.Y.Z>.md`, nothing else. With `release.note_reviewer` too, a task **« Review the unified release note of <X.Y.Z> »** (`step=review`), assigned to the reviewer, is blocked by the writing task. Each of these tasks `blocks` the release issue, so there is no GO, hence no publication, until the last of them is resolved (§8); tasks the bridge could not create or relate hold the GO that tick, fail-closed. Each task is found again by its marker, never created twice, and a missing relation is written at the next tick. With a writer, those note files are bookkeeping after the candidate (§8), and once the note is written there the GO tags the release branch's tip, read in the same comparison that checked it, instead of the candidate's commit, and reads the notes there (§9): the note follows the same path to GitHub and to the apps as before. The tip is tagged only when it differs from the candidate by the note files and that candidate's own angle reports, which is what `release-publish` lets follow a candidate; any other file (a configured bookkeeping path included) holds the GO and says so. Should the publication of such a tag be retracted, the candidate gets no second GO, whichever commit was tagged. A writer configured once a release's first candidate was cut takes effect at the next release. Without a writer, nothing changes: no task, and the release notes are the tickets' notes as the cut prepared them.
13. **Abandoning a cycle** keeps the RC tags, merges the release branch back into `main` so that merged fixes are not lost, cancels the release issue, turns each remaining blocker into a ticket, and the next cut starts a new cycle from `main`. The new cycle gets its own release issue (the canceled one is never reused nor written again), and its passes count from its own first candidate: when the version was kept, its first candidate (say `rc.5`) is pass 1 for `max_rc_passes` (§10), for the policy of later passes (§7) and for the creation of the release note's tasks, whatever its RC number.
14. **A release the bridge did not open is not its cycle.** A version already published with no release issue of the bridge (a release made before the bridge took the product over) is left alone: no issue, no closure, no note. The bridge's first cycle on a product is the first one cut after it took over.
15. **A patch ships a fix to production beside an open cycle** (ASDLC-MG26, rules K4PT, R7WM, Q3HV, T9BX). `spl-asdlc release patch --pr <n>[,<n>…]` reads the release in production (the highest release tag with a published GitHub release), refuses a PR that is not merged, was merged into another base or is already in production, and refuses a patch whose version (production + 0.0.1) already has a cycle; it then dispatches the cut workflow on the default branch with `action=patch`, `version` and `pulls`. The cut's `patch` action cuts `release/<stamp>-utc` from the production tag, never from `main`, and is not blocked by a cycle in flight; it reads each PR as the App, refuses any whose merge commit `main` does not hold, cherry-picks the merge commits with `-x` in the order `main` took them (`-m 1` for a merge commit, a conflict refusing the patch with nothing pushed), prepares the release (notes from the commits since the production tag, each cherry-pick embarking the ticket of the PR it copies by its `(cherry picked from commit …)` line), and pushes the branch and rc.1 as the App, the tag annotated with `Release-Patch-From: <production tag>` and `Release-Patch-Pulls:`. The release pass carries every patch in flight (a lower version above production whose first candidate carries that line) beside the newest cycle, with its own release issue and QA round under the usual rules (§3–§8, angles on their changed paths over the diff since production), patches first and one merge per tick at most; the open cycle is untouched. With several cycles in flight, `release cut`, `release status` and `release abandon` name the cycle by `--branch`; abandoning a patch deletes its branch with no merge back. The GO copies `Release-Patch-From:` into the patch's release tag; the publication then merges the patch branch into the one other release branch in flight as a merge commit, never into `main` (several possible open cycles are refused, none leaves `main` untouched), and deletes the patch branch. The patch closes (§11) once its branch is gone and its tag is in the open cycle. The open cycle's branch has then moved past its candidate: that candidate gets no GO (§8), and the next one is cut on the open branch (§7).

## The brief

Posted by the bridge on the release issue once per RC, once that RC's gate is green (§3): the candidate (tag, commit, class), the range, the embarked tickets with their acceptance criteria (each ticket is found by commit → PR → linked ticket, never by text; the bridge's own review items linked to a PR are not tickets, §11), the business rules touched (the rule files of `.spl-asdlc/business-rules/` the range changes), the link to the evidence pack, the angles and their sub-items. A range, PR, link or evidence pack that cannot be read makes the brief fail; it is never guessed or left empty, and the angle sub-items wait with it, so that no agent starts without its brief.

GitHub lists at most 300 files of a comparison. A range whose list GitHub cut is still read (rule G7CK): its commits are complete, so its tickets are found and labelled, and its brief is written; the brief says the list was cut at 300, and its paths and business rules touched are the first 300 only. A cut list counts as touching every reviewed path (rule X4PV): the brief and the candidate's comment give the class `sensible` whatever the tag says, every configured angle is offered as on any candidate, and a release branch that moved past its candidate by a cut list is a tip gap.

## The range and the first release

A candidate's range is Git's: the commits of the candidate that the highest published release below its version does not contain. The version and the notes `release prepare` writes (§1), the release class the cut computes, the gate's evidence pack, the embarked tickets, the brief and the closure (§11) all read this one range.

**A product's first release needs no base tagged by hand.** With no published release below the candidate, the range is the candidate's whole history, measured from the repository's root, and each step says so:

- the cut computes the class on every file of the history and records the base `root` in the tag (`Release-Class-Base: root`), so a first release whose history holds a reviewed path is `sensible` (the reviewed paths are the union of the `paths` of `[[review.angles]]` in the configuration at the candidate: with none, no path is reviewed apart and the class is `routine`; a configuration whose angles' paths cannot be read makes it `sensible`);
- the gate does not fail: its `last-tag` output is empty, and its log, `run.json` and `results/suites.json` (`lastReleaseTag` and `from_tag` null) and its report say the candidate is measured from the repository's root; the PR guards it re-runs get the empty tree as `BASE_SHA`;
- the brief reads "Diff since the repository's root: first release", and lists every path at the candidate;
- `release prepare` reads the whole history and bumps the version from `0.0.0` (a `feat` makes it `0.1.0`), unless `--version` forces the first one; its CHANGELOG heading has no compare link;
- `doctor` reports the release base it finds, or that the first candidate will be measured from the root.

## Configuration (per project)

- Release shape: candidate tag pattern, final tag pattern, the record file, the version files besides Rust's own, the CHANGELOG sections.
- Release angles with assignee hints, or `angles = []` for a release with no QA angle (§3); the tracker participant who receives the consolidation item (`release.coordinator_assignee`, optional); `max_rc_passes` (default 2); the policy for later passes (`full` | `gate-and-coordinator`); GO policy (`computed` | `human`); the release fixer who receives the urgent fix tickets (`release.fix_assignee`, optional).
- Publication and deployment steps (inputs of `release-publish`); the binary channel of the cut (`spl-asdlc-version`). A caller may name repositories under its GitHub owner in `dependent-repositories`; after a publication, each receives a `repository_dispatch` whose type is `spl-asdlc-published` and whose payload names the source repository and release tag. A dependent handles that fact through its normal reviewed update and release path; the notification never changes it directly.
- Notification channels for the release note.

**One product, one version.** A release has one version, one tag, one CHANGELOG section and one publication. A product built for several platforms from that version (desktop, mobile, web, server binaries) is still one product: its publication job builds and deploys every target, and a target that reaches production later (a store's review) is verified through the ticket's `## Post deploy` section. Deliverables versioned and released independently of each other (multi-component products) are not supported: such a product is set up as one repository per deliverable, or waits for that support.
