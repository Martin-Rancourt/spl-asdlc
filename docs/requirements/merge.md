# Requirements — merge pass, ticket contract and business-rule guards

This document is the contract for the Rust rewrite (crate `<prefix>-asdlc`, "the bridge") of AgentForge's deterministic merge pass (`pr_merge.py`), its ticket guards (zero-boxes-checked guard, Done gate, ticket contract, business-rule guard) and the tracking comment (`linear_tracking.py`). The bridge runs in the user's environment, polls GitHub, never asks a model anything, and writes to a tracker through a `Tracker` trait (Linear or Livela). Canonical status names are "In Progress", "In Review", "To Deploy", "Post Deploy", "Done"; the tracker adapter maps them. Per-repo configuration comes from `<prefix>-asdlc.toml` plus `.github/review-paths.json`. All Python references are to `origin/main` (commit f30f3699) of AgentForge; `pr_merge.py:N` means line N of `src/agentforge/pr_merge.py`. Where the Python routes "one reviewer agent", the target creates one sub-item per review angle plus one consolidation item; those points are marked **Replaced**. Behaviour that exists only because of AgentForge's fleet (agent identities, 2Do, Telegram, vault tables) is listed in "Dropped from the Python". Every free-text message the bridge writes to the tracker or to GitHub is in English (REQ-MERGE-070); machine-readable markers are English keys.

Conventions used below: "fail closed" means the bridge takes no irreversible action (no merge, no status promotion) and says why; "unreadable" always means "a read was attempted and did not return a trustworthy answer", which is never the same answer as "there is nothing". "Head SHA" is the PR's head commit id at the moment of the poll. "Tick" is one run of the pass over all configured repos.

## Requirements

### Candidate selection

**REQ-MERGE-001 — The bridge lists the open PRs of every configured repo each tick, and distinguishes "no open PR" from "could not list them".**
An empty list is a normal, silent outcome. A failed or malformed listing makes the pass blind on that repo: nothing is merged, routed or updated there this tick, one decision `skip` ("cannot list its open PRs (<cause>)") is recorded, and the blind notice of REQ-MERGE-081 is raised.
Source: `pr_merge.py:633-664` (`read_open_prs`), `pr_merge.py:3795-3815`.
Notes: Python reads at most 30 PRs per tick (`limit=30`, `pr_merge.py:633`), in `gh pr list` order (most recently updated first, per the comment at `pr_merge.py:4260`). The target must define pagination and ordering explicitly (see Open questions Q1, Q2). A listing that parses but is not a JSON list is also "unreadable". A token that can list PRs but not read their check rollup is the real-world cause (2026-09-24/25) and must read as unreadable, not as empty.

**REQ-MERGE-002 — Every PR is judged against its own base branch; no branch name is hard-coded.**
Required checks, the sensitive-path list, "behind" and the up-to-date requirement are all resolved per PR base (e.g. `main` and a short-lived `release/<date>` branch live at the same time). A PR whose base is a release branch is an ordinary PR (hotfix) and merges like any other.
Source: `pr_merge.py:3779-3797` (docstring), `pr_merge.py:3823-3860` (per-base caches), `pr_merge.py:3984-3987`.
Notes: per-base reads are cached for the tick (one required-check read and one sensitive-list read per base, however many PRs share it). Python's `base` defaults to `main` only when the API returns no base (`pr_merge.py:482`). An unreadable required-check list closes that base for the tick, not the whole repo (REQ-MERGE-014).

**REQ-MERGE-003 — A release-please PR is never touched.**
A PR is a release-please PR if its head branch starts with `release-please--` OR its title matches (case-insensitive) `^chore\(.*\):\s*release\b`; either signal alone is enough. It yields decision `skip` ("release-please PR — a maintainer merges it"), no tracker write, no merge, and the tickets its body cites are never treated as its delivery ticket.
Source: `pr_merge.py:107-108`, `pr_merge.py:1479-1485`, `pr_merge.py:3893-3897`.
Notes: merging it cuts a release, which is a deliberate human act. Making the branch prefix/title pattern configurable per repo is allowed; the defaults above are the contract. Test: `test_a_release_please_pr_citing_a_to_deploy_ticket_does_not_reopen_it` (no tracker write at all even when the body cites a ticket URL).

Superseded 2026-10-12: the release cycle opens no release PR: it prepares the version on the release branch and tags the release itself (`docs/spec/05-release-cycle.md` §1, §9). A PR shaped like release-please's is an ordinary PR to the merge pass, judged like any other; the label `release.release_pr_label` is gone.

**REQ-MERGE-004 — A release-record (gate-record) PR is never merged by the pass.**
A PR whose head branch starts with `release-record/` is skipped ("gate-record PR — the release pass merges it") and is never treated as the delivery of the ticket its title cites.
Source: `pr_merge.py:1488-1498`, `pr_merge.py:3898-3902`.
Notes: it is merged by the release machinery (another area). The prefix should be configurable; the default is the Python literal.

Superseded 2026-10-12: the gate record PR is gone with the multi-component shape; a `release-record/` head is an ordinary PR.

**REQ-MERGE-005 — A merge-back PR (release branch into main) and the PR that resolves a conflicted merge-back are never merged by the pass, and are excluded before anything else is read.**
Detection is on the HEAD branch, never the base: head starts with `release/`, OR head starts with `chore/merge-back-`, OR the head is empty/unreadable (an unreadable head is treated as a merge back). A PR whose BASE is `release/...` is NOT a merge back. Exclusion happens without reading a diff, a ticket or checks. Reasons recorded: "the head branch could not be read — refusing to squash what may be a merge back"; "resolution of a merge-back conflict — merged by hand, as a merge commit, never squashed"; "merge back of a release branch — the release close merges it, as a merge commit".
Source: `pr_merge.py:1500-1553`, `pr_merge.py:3903-3913`.
Notes: reason for the rule: the pass only squash-merges, and a merge back must be a merge commit so the release tag becomes an ancestor of main; squashing would corrupt every later changelog. Fail-closed on empty head is deliberate: skipping an ordinary PR costs one tick, squashing a merge back is silent corruption. The literal `chore/release-mergeback-sync` is an instance name and is dropped (see Dropped); the prefixes should be configurable. `chore/merge-backlog` must NOT match (prefix is `chore/merge-back-` with the trailing hyphen).

**REQ-MERGE-006 — A draft PR is never merged and never sent to review.**
Decision `skip` ("draft"). The draft check comes after the terminal-ticket reopen of REQ-MERGE-028 (an open draft is still proof that a terminal ticket is wrong) and before required checks are read.
Source: `pr_merge.py:3983-3986`.
Notes: none beyond ordering.

**REQ-MERGE-007 — For each non-excluded PR the pass evaluates, in this order, and stops at the first outcome.**
(1) disarm a native auto-merge armed on a stale head SHA (REQ-MERGE-020); (2) exclusions 003/004/005; (3) board-write link → ticket read → archived skip → terminal-ticket reopen (REQ-MERGE-027/028); (4) draft; (5) required checks of the base (unreadable → skip the PR, REQ-MERGE-014); (6) full ticket-link resolution (none/ambiguous → skip + notice, REQ-MERGE-024/025); (7) ticket read + archived skip; (8) check state (red → report and skip; none+conflicting → update path; pending/none → skip, REQ-MERGE-012); (9) read changed paths; (10) business-rule guard (REQ-MERGE-041); (11) zero-boxes guard (REQ-MERGE-031); (12) review triggers and approval (REQ-MERGE-044..056); (13) up-to-date classification (REQ-MERGE-016); (14) the queue (REQ-MERGE-008).
Source: `pr_merge.py:3869-4293`.
Notes: ordering is part of the contract because several guards must not run on PRs that fail earlier ones (e.g. the registry is not read for a red PR; the diff is not read for a merge back). **Replaced**: step (12) in Python routes a reviewer agent; in the target it creates angle sub-items (REQ-MERGE-051).

**REQ-MERGE-008 — At most ONE merge per repository per tick, across all bases; branch updates are not subject to that queue.**
Among the PRs classified mergeable (green, no outstanding review hold, up to date), the first in listing order is merged; every other mergeable PR gets decision `skip` ("another PR merged first this tick — this one is behind now"). A PR classified as needing a branch update waits ("waiting behind the merge queue") whenever a merge happens this tick. If no PR is mergeable, every PR needing an update is updated in the same tick (REQ-MERGE-017).
Source: `pr_merge.py:4257-4334`.
Notes: reason: after any merge every other PR on that base is behind; a second merge in the same tick would land code never tested against the new base. The queue is per repository, not per base (a repo is one CI/runner). If the single chosen merge is refused by GitHub, the other mergeable PRs are STILL skipped this tick (Python does not fall through to the next candidate); the target may keep this (simplest) but must record it (Open question Q3). Ordering tie-break must be deterministic (Q2).

**REQ-MERGE-009 — A failure in one repository never costs the other repositories; the merged-PR sweep never costs the tick.**
Per repo: act on open PRs, then sweep recently merged PRs; an exception in either is logged and the next repo proceeds. A journal write failure never undoes or aborts a merge.
Source: `pr_merge.py:4927-4979` (`run_pass`), `pr_merge.py:1988-2003` (`append_action`).
Notes: `test_a_journal_write_never_raises`.

### Green, up to date, required checks

**REQ-MERGE-010 — "Green" is computed from the PR head's check rollup as exactly one of `green`, `red`, `pending`, `none`.**
`none` = the rollup contains no check at all (never treated as green: "no check failed" is not "something verified it"). `red` = any check (after REQ-MERGE-011 reduction) whose conclusion-or-state is in {FAILURE, ERROR, TIMED_OUT, CANCELLED, ACTION_REQUIRED, STARTUP_FAILURE, STALE}. `pending` = no red, and any check whose status or conclusion/state is in {QUEUED, IN_PROGRESS, PENDING, WAITING, REQUESTED}. Otherwise `green`. `red` wins over `pending`. SKIPPED, NEUTRAL, SUCCESS are all non-failing and non-pending. For legacy commit statuses the field `state` is used where `conclusion` is absent. Comparison is case-insensitive.
Source: `pr_merge.py:176-181`, `pr_merge.py:1194-1211`.
Notes: only `green` can lead to a merge. REST mapping: check runs (`status`/`conclusion`) and combined commit statuses (`state`) must both be folded into the same rollup.

**REQ-MERGE-011 — Only the latest run of each check counts.**
A check is identified by (workflow name, check name). Its latest run is the one with the greatest `startedAt`; a run not yet started (null or zero-time `0001-01-01…` start) is newer than any started run, so a re-run in flight reads `pending`, not the red it replaces. Runs the timestamps cannot order are all kept. Two checks with the same job name in different workflows are two checks (a later green in one never hides a red in the other). Entries with no name are kept as-is.
Source: `pr_merge.py:1147-1191`.
Notes: GitHub lists every run the head commit has had (e.g. a draft run and a ready-for-review run); fixing a PR title re-runs the title check on the same commit, and the old red must not outlive the fix. Tests: `test_a_red_run_superseded_by_a_green_rerun_on_the_same_commit_is_green`, `test_a_green_run_superseded_by_a_red_rerun_is_red`, `test_a_rerun_not_started_yet_is_pending_not_the_red_it_replaces`, `test_one_job_name_in_two_workflows_is_two_checks`.

**REQ-MERGE-012 — Non-green PRs are handled as follows, and a non-green PR is never merged.**
`red`: skip ("CI is red") and report to the ticket (REQ-MERGE-013). `pending`: skip ("checks have not reported yet"). `none`: skip ("no checks reported"). Exception: `none` AND the PR is conflicting (mergeable state CONFLICTING or merge state DIRTY) is treated as a conflict and goes to the update path (REQ-MERGE-017), because GitHub runs no pull-request workflow on a conflicting PR so "no checks" never ends there.
Source: `pr_merge.py:4045-4089`.
Notes: a PR that conflicts and has `none` checks never gets native auto-merge armed after a successful update (REQ-MERGE-019): its new head still needs CI and every review gate.

**REQ-MERGE-013 — A red PR is reported to its ticket once per head SHA, with the first failing check, a link to its run, and the tail of its job log.**
Content: `job: <name of the first failed check in the rollup>`, `run: <details URL, else the PR URL>`, and, when the details URL carries a job id (`/actions/runs/<run>/job/<job>`), the last 30 lines of that job's log in a fenced block. Best-effort: a log that cannot be fetched never stops the report (the run link alone is enough); no failing check found yields a "(no failing check found in the status rollup)" line. The log fetch is lazy: it is performed only after the dedup guard has decided there is a comment to write (never for an already-reported head). If the ticket is already "In Review", the report is instead the "checks finished (red)" line of the tracking block (REQ-MERGE-069). The report is written whatever the ticket's status (status is a write destination, never a condition).
Source: `pr_merge.py:1242-1285` (`ci_failure_detail`), `pr_merge.py:3459-3533` (`ci_failed`), `pr_merge.py:4045-4066`.
Notes: dedup key = (ticket, kind `ci_failure`, head SHA), recorded only after the comment was successfully written (REQ-MERGE-078). **Replaced**: the Python also reassigns the ticket off a "host voice" author and tags (@mentions) the author to wake it; both are agent-fleet mechanics and are dropped. Tests: `test_a_red_pr_reports_the_failing_job_to_its_ticket`, `test_a_red_pr_is_reported_once_per_head_sha`, `test_a_deduped_red_pr_does_not_download_the_job_log`, `test_ci_failure_detail_names_the_job_and_tails_its_log`, `test_ci_failure_detail_survives_a_log_that_cannot_be_read`.

**REQ-MERGE-014 — The set of required status checks of a base is read from branch protection AND from active rulesets; the answer is tri-state; an unreadable answer fails closed for that base.**
Answers: a set of names; the empty set (the API said there are none); or UNREADABLE. Classic branch protection: a 404 is an answer ("no protection rule" = empty set); any other failure (5xx, rate limit, timeout, missing scope, no answer) is UNREADABLE. The classification is by HTTP status only, never by message wording ("not found" in free text is not a 404). The result is the union of the classic set and the ruleset set; if either half is UNREADABLE the whole answer is UNREADABLE (a missing half is not "no required checks"). UNREADABLE closes the base for the tick: every PR on that base is skipped ("the required-check list of `<base>` could not be read") and the blind notice of REQ-MERGE-081 is raised; other bases of the same repo proceed.
Source: `pr_merge.py:752-808` (`_classic_required_contexts`), `pr_merge.py:1040-1060` (`required_contexts`), `pr_merge.py:597-619` (`_gh_http_status`), `pr_merge.py:3984-4006`.
Notes: the skipped-required-check trigger (REQ-MERGE-050) is read from this list, so a rule that could not be read is a rule that did not run. `required_contexts` costs two reads per base (classic + rulesets list, plus one read per active ruleset). Tests: `test_required_contexts_separates_no_protection_from_no_answer`, `test_a_404_on_the_protection_endpoint_is_an_answer_whatever_its_message`, `test_words_without_a_404_are_not_an_answer_about_protection`, `test_gh_http_status_reads_the_status_gh_reports_and_nothing_else`, `test_an_unreadable_required_check_list_stops_the_whole_repo`, `test_a_branch_with_no_protection_rule_is_an_answer_not_a_failure`, `test_the_required_check_list_is_read_once_per_base`, `test_the_required_checks_are_read_for_the_prs_own_base`.

**REQ-MERGE-015 — Ruleset reading rules.**
Only rulesets with target `branch` AND enforcement `active` are considered. The detail of each is read; a ruleset applies to a base when the base's ref (`refs/heads/<base>`) matches an `include` pattern of its `conditions.ref_name` and no `exclude` pattern. Pattern forms: `~ALL` (matches every ref), `~DEFAULT_BRANCH` (matches when the base equals the repository's real default branch), otherwise a shell-style glob against `refs/heads/<base>` in which `*` and `**` also match `/`. The contexts of every `required_status_checks` rule of an applicable ruleset are added to the set. The default branch is resolved from the repository at most once per read, and only if a branch/active ruleset needs it; if that single read fails it falls back to `main` (this refinement is NOT part of the fail-closed core). A failure to list rulesets, or to read the detail of any active branch ruleset, makes the whole answer UNREADABLE. A malformed (non-JSON, non-list/dict) ruleset answer is UNREADABLE.
Source: `pr_merge.py:810-1007`.
Notes: reason for resolving `~DEFAULT_BRANCH` for real: assuming `main` fails in the unsafe direction (required checks silently dropped). Tests: `test_a_ruleset_is_read_when_the_classic_api_sees_no_protection`, `test_a_ruleset_is_combined_with_a_real_classic_answer`, `test_a_ruleset_targeting_a_different_branch_does_not_leak_in`, `test_an_inactive_or_non_branch_ruleset_is_ignored`, `test_an_unreadable_ruleset_list_stops_the_read`, `test_an_unreadable_ruleset_detail_stops_the_read`, `test_a_default_branch_ruleset_matches_the_repos_real_default_branch`, `test_an_unreadable_default_branch_falls_back_to_main_not_to_unreadable`, `test_the_default_branch_is_resolved_once_not_once_per_ruleset`.

**REQ-MERGE-016 — "Up to date" is a classification of the PR's merge state; only an up-to-date, conflict-free, green, hold-free PR is mergeable.**
Classification, evaluated after every review/guard check: conflicting = (`mergeable` == CONFLICTING) OR (merge state == DIRTY) → needs a branch update, flagged "conflicted"; merge state BEHIND → needs a branch update (not conflicted); anything else (CLEAN, BLOCKED, UNSTABLE, HAS_HOOKS, UNKNOWN, empty) → mergeable. A BLOCKED merge state is NOT a reason to skip (rulesets that read BLOCKED to everyone including bypass actors are enforced by GitHub itself at merge time).
Source: `pr_merge.py:4141-4146`, `pr_merge.py:4235-4254`, `pr_merge.py:4376-4382` (docstring).
Notes: a conflicting PR is never merged in the same tick; the update attempt is the "up to date" fact (the `mergeable` flag can be stale). Merge-state UNKNOWN / `mergeable: null` (GitHub still computing) is treated as mergeable by Python (Open question Q4). Tests: `test_a_conflicting_pr_is_never_merged_in_the_same_tick`, `test_a_green_but_behind_pr_is_brought_up_to_date_not_merged`, `test_a_base_under_an_update_ruleset_is_merged_through_rest`.

**REQ-MERGE-017 — A PR that is behind or conflicting is brought up to date with the base by the REST update-branch call, never by rebase, and every such PR is updated in the same tick when no merge happens.**
The call merges the base into the head (HTTP PUT `…/pulls/<n>/update-branch`; 202 = accepted). On success: journal `update-branch` (with `base`, `issue`, and `resolved_conflict: true` when the PR was conflicting), decision `update-branch` ("green but behind the base branch" / "was conflicting, updated cleanly against its base"), and nothing else happens this tick (the head changed, CI restarts, a later tick reads the new state). On failure: if the PR was flagged conflicting AND the failure status is exactly 422 → real conflict (REQ-MERGE-018); any other failure (rate limit, permissions, 5xx, "422" appearing only in free text) → decision `skip` ("refused the branch update (<cause>)"), no report to the ticket.
Source: `pr_merge.py:4474-4571` (`_update_branch`), `pr_merge.py:4304-4333`.
Notes: updating in parallel is allowed because it touches no base. Tests: `test_a_behind_pr_is_updated_through_the_rest_api_gh_245_has_no_subcommand` (REST only), `test_every_behind_pr_is_updated_in_the_same_tick`, `test_behind_prs_wait_a_tick_when_a_merge_happens_instead`, `test_a_merge_wins_over_a_branch_update_in_the_same_tick`, `test_conflicting_and_behind_prs_are_all_updated_in_the_same_tick`, `test_a_conflicting_pr_that_resolves_cleanly_is_updated_not_reported`, `test_a_conflicted_prs_ordinary_gh_failure_is_not_reported_as_a_conflict`, `test_a_conflicted_pr_with_no_checks_is_tried_as_a_conflict`.

**REQ-MERGE-018 — A confirmed conflict (update-branch answered 422 on a conflicting PR) is reported once per head SHA and the ticket goes back to "In Progress".**
The ticket status is set to "In Progress" even from a terminal status (Done / To Deploy): "In Progress" here means "somebody needs to act", not that the ticket's scope reopened. The message states that the PR conflicts with `<base>`, that bringing the branch up to date failed, and that the author must rebase/resolve and push; the pass retries the update every tick. Decision `skip` ("conflicts with the base branch — update-branch failed, needs a manual rebase"). Only a CONFIRMED conflict is reported (a generic failure is not pinned on the author). Dedup: once per (ticket, kind `conflict`, head SHA).
Source: `pr_merge.py:3588-3665` (`conflict`), `pr_merge.py:4523-4545`.
Notes: **Replaced**: the Python also resolves the PR author (GitHub App login `app/<prefix>-<agent>` or `<prefix>-<agent>[bot]`) to a Linear user, assigns the ticket to them, unassigns host-voice/human authors and @mentions the agent; all dropped. Whether the adapter should assign the ticket to the PR author is Open question Q5. Tests: `test_a_real_conflict_is_reported_to_its_ticket_once_per_head_sha`, `test_a_real_conflict_with_no_checks_goes_back_to_its_author`.

**REQ-MERGE-019 — (Optional feature, off by default) A green, hold-free PR that this tick does not merge itself may have GitHub's native auto-merge armed.**
Eligible PRs: the runner-up mergeable PRs of the tick, and a green-but-behind PR after its branch update succeeded. NOT eligible: a conflict-path PR (it entered with no checks; its new head needs CI and every gate), a PR whose update failed, a PR whose conflict was confirmed. Armed only if the repo config opts in (`native_auto_merge`, default false; never a repository-wide setting) AND the base requires an up-to-date branch (REQ-MERGE-021; an unreadable answer counts as "no"). Method: squash, to match the pass's own merge method. A failed arm never breaks the tick and is retried only by a later eligible tick; on success journal `arm-auto-merge` (`repo`, `pr`, `issue`) and record the head SHA armed (REQ-MERGE-020).
Source: `pr_merge.py:4276-4333`, `pr_merge.py:4669-4733`.
Notes: it is a courtesy speedup, not a second path to merging: the PR was already classified green with no hold by this pass. A polling pass cannot out-race a push it has not yet seen; residual race is documented in the Python. Whether the bridge keeps this feature at all is Open question Q6. Tests: `test_native_auto_merge_is_off_by_default`, `test_native_auto_merge_arms_the_runner_up_pr`, `test_native_auto_merge_arms_a_behind_pr_after_its_update`, `test_native_auto_merge_is_not_armed_after_a_conflict_update_without_checks`, `test_native_auto_merge_is_not_armed_after_a_failed_branch_update`, `test_native_auto_merge_is_not_armed_on_a_confirmed_conflict`, `test_a_failed_arm_does_not_break_the_tick`.

**REQ-MERGE-020 — (Optional feature) A native auto-merge armed on a head SHA that a later commit replaced is disarmed at the top of the tick, before any state-based early exit; a PR newly needing review is also disarmed.**
The bridge records, per `<repo>#<pr>`, the head SHA it armed (with a timestamp; entries older than 30 days are pruned; the write is atomic). At the top of the per-PR loop, a PR that GitHub reports as armed AND whose recorded SHA differs from its current head is disarmed whatever state its checks are in (a `pending` tick must not skip the disarm). A PR the bridge did not arm (no recorded entry, e.g. a human ticked the box) is never considered stale. A PR that this tick re-classifies as needing review while armed is disarmed too (journal `disarm-auto-merge`). The recorded entry is cleared after a disarm and after a merge. A failed disarm never breaks the tick and is not journaled.
Source: `pr_merge.py:4574-4666`, `pr_merge.py:3878-3891`, `pr_merge.py:4160-4177`, `pr_merge.py:4736-4776`.
Notes: tests: `test_a_pr_needing_review_disarms_its_stale_native_auto_merge`, `test_a_pr_needing_review_with_no_stale_auto_merge_never_calls_disarm`, `test_a_failed_disarm_does_not_break_the_tick`, `test_a_new_commit_disarms_a_pending_pr_before_it_can_race_to_merge`, `test_an_armed_pr_on_its_original_sha_is_not_disarmed_by_a_pending_check`, `test_a_merge_clears_its_own_recorded_arm_state`.

**REQ-MERGE-021 — (Optional feature) `requires_up_to_date_merge(base)`: true when branch protection OR an applicable active ruleset on the base enforces "branches must be up to date before merging".**
Classic: the `strict` field of the required-status-checks protection (a 404 means false; any other failure is UNREADABLE). Rulesets: any applicable active branch ruleset whose `required_status_checks` rule has `strict_required_status_checks_policy` true. Result: true if either says true; UNREADABLE only if every half that did not say true was unreadable; else false. An UNREADABLE result is treated exactly like false by the caller (it only costs a speedup, never a merge). The existence of a required check is a DIFFERENT setting and must not be used as the proxy.
Source: `pr_merge.py:1063-1144`, `pr_merge.py:1010-1037`.
Notes: tests: `test_native_auto_merge_never_arms_without_an_up_to_date_requirement`, `test_native_auto_merge_never_arms_on_a_required_check_that_is_not_strict`, `test_native_auto_merge_arms_when_a_ruleset_enforces_the_up_to_date_policy`.

### Ticket link

**REQ-MERGE-022 — The ticket a PR serves is resolved from, in priority order: branch name, an explicit tracker link, the title, an explicit body line, a lone body mention.**
(a) Branch: matches `(?:^|/)<key>-<number>(?:-|$)` with a 2-5 letter key, case-insensitive, after an optional leading `<segment>/` (so `claude/abc-313-lot-b`, `someone/abc-571-x`, `abc-7-plain` all resolve); the identifier is upper-cased (`ABC-313`). (b) A body line of the form `Closes|Fixes|Resolves <tracker issue URL>` (case-insensitive, line-anchored). These two are the "board-write" link (REQ-MERGE-026). Then text sources, only when (a)/(b) found nothing: (c) the title when it contains exactly one distinct ticket identifier of a known team key; else (d) a body line that names a ticket on purpose (`Linear:`/`Closes`/`Fixes`/`Resolves` followed by an identifier, optional leading bullet, optional colon) when exactly one distinct such identifier exists; else (e) the body's single bare identifier, only when the title and explicit lines yielded none and the body contains exactly one distinct identifier.
Source: `pr_merge.py:107-153`, `pr_merge.py:1360-1466`.

### Ticket contract (zero boxes checked, Goal + acceptance criteria)

**REQ-MERGE-030 — One shared reader extracts the checkbox lines of a ticket description; every guard uses it.**
A checkbox line matches (multi-line mode) `^[ \t]*(?:[-*+]|\d+[.)])[ \t]+\[([ xX])\].*$`: any markdown bullet (`-`, `*`, `+`, `1.`, `1)`), any run of spaces/tabs after it (`-   [ ] a` counts), mark space = open, `x` or `X` = checked. The reader is heading-agnostic: a box counts under any heading or none. Fenced code blocks are exempt (quoted material, not the ticket speaking): a fence line is `^[ \t]{0,3}(?:`{3,}|~{3,})`; the first fence line opens a block and the next fence line closes it (any fence character, any length: deliberately forgiving); the lines of the block including both fence lines are blanked, line count preserved. A fence that is never closed is NOT a block: nothing is blanked (blanking to end of text would hide every criterion below a stray fence, a fail-open). Lines are returned verbatim (original markdown spelling) as two lists: checked and open.
Source: `linear_service.py:323-325`, `linear_service.py:352`, `linear_service.py:1215-1239` (`_without_fenced_blocks`), `linear_service.py:1242-1266` (`completion_checklist_items`).
Notes: product decision (a past incident): a checkbox engages everywhere; a note that must not engage is written as a plain bullet. Tests: `test_completion_checklist_items_reads_a_box_under_any_heading`, `test_completion_checklist_items_reads_every_markdown_bullet_spelling`, `test_completion_checklist_items_ignores_a_box_inside_a_fenced_block`. **REQ-MERGE-036 — A "new rule" is a statement in the Business rules section that is not an absence declaration and cites no rule id; the first such statement is quoted back.**
Statements are units of meaning, not lines. Algorithm (`section_items`): process the section body line by line, each line stripped; a blank line or a thematic break (`^(?:-[ \t]*){3,}$|^(?:\*[ \t]*){3,}$|^(?:_[ \t]*){3,}$`, so `---`, `***`, `___`, `- - -`, `* * *`, `_ _ _`) closes the current item and the next line starts a fresh one; a line that begins a new item (matches, on the STRIPPED line, `^(?:[-*+]\s+|\d+[.)]\s+|#+\s|>\s|\|)`: list bullet needing a space, ordered marker, heading, quote, table row) closes the current item and starts a new one; any other line is joined (single space) to the current item (lazy continuation, indented or at column zero). A NESTED bullet (indented) is judged on the stripped line and therefore opens its OWN item — it must never be folded into its parent, or a new rule could ride in under a sibling that cites an id (the one fail-open this reader has). Then for each item: strip one leading list marker `^(?:[-*+]|\d+[.)])\s*`, then one leading checkbox `^\[[ xX]\]\s*`; skip the item if it is noise (empty, or only a bare list marker / table separator row `\|[\s:|-]*\||` bare `#+ ` / bare `>`: regex `^(?:[-*+]\s*|\d+[.)]\s*|\|[\s:|-]*\||#+\s|>\s*)?$`), if it declares absence (REQ-MERGE-037), or if it contains a rule id (`RULE_ID_RE.search`); otherwise it is the new-rule statement. The first such statement is returned (and quoted in the refusal); `declares_new_rule` is "a statement exists".
Source: `business_rules.py:62-85`, `business_rules.py:115-152` (`section_items`), `business_rules.py:175-210`.
Notes: reason (a past incident): reading line by line made the second line of a wrapped rule that cites `BR-AF-004` look like an anonymous new rule, and PR #733 was refused every tick. Observed Python quirks the implementer must either reproduce or decide on (Open question Q11): a sub-heading WITH text (`### Détail`), a quote line (`> text`) and a table header row (`| ID | Règle |`) are NOT noise (the noise regex only matches the bare marker), so, when they cite no id, they read as new-rule statements. Tests: `test_a_heading_or_a_table_row_is_not_a_new_rule`, `test_a_cited_rule_wrapped_over_two_lines_is_not_a_new_rule`, `test_a_continuation_left_at_column_zero_still_belongs_to_its_rule`, `test_a_thematic_break_is_punctuation_not_a_rule`, `test_a_wrapped_rule_without_an_id_is_still_refused`, `test_section_items_regroups_lines_into_statements`, `test_a_nested_bullet_is_its_own_statement_not_its_parents_continuation`, `test_section_items_splits_on_every_marker_it_names`, `test_a_rule_of_process_cited_without_an_id_is_still_a_new_rule`.

**REQ-MERGE-039 — The guard judges a ticket's cited ids and new rules against the registry of the product at the judged ref; it never reads the registry itself in the judgement function.**
**Corrected by the specification** (`docs/spec/02-business-rules.md` §4-6): a registry absent at the judged ref does not switch the guard off. A ticket that cites a rule id is refused (the id cannot exist in a registry that does not exist); a ticket that states a new rule needs a PR that creates the registry with it; a ticket that neither cites nor states a rule is judged without reading the registry, as before.
`evaluate(description, registry, changed_paths)`: `registry == None` means the product keeps no registry: the guard is OFF (ok, `registry_present = false`), never a refusal. Otherwise: (a) unknown ids = cited ids not in the registry, restricted to the prefixes the registry owns (`owned = {rule_prefix(id) for id in registry}`); an id of another product's prefix is left to that product's own guard; if the registry declares nothing (`owned` empty) every cited id is judged; the unknown ids are sorted. (b) Promotion half, only when the changed paths are known: if a new-rule statement exists and no changed path (backslashes normalised to `/`) ends with `docs/business-rules.md`, then `unpromoted = true` and the statement is kept for quoting. When `changed_paths` is unknown (`None`, e.g. no diff to read) the promotion half is skipped but unknown ids are still caught. A rule promoted AND cited by its new id in the SAME PR passes (the registry judged is the PR head's, which contains it). `ok` = no unknown ids, not unpromoted, not unreadable. A statement is carried in the gate only when unpromoted; an unknown-id-only refusal quotes nothing.

**REQ-MERGE-073 — A merge already contained in a published FINAL release tag of the component that owns it is not promoted again by the sweep.**
Ownership comes from the repo's release-please config (`release-please-config.json` or `.release-please-config.json`; the `packages` map; per-package `include-component-in-tag` default true, `component` or `package-name`, `tag-separator` default `-`). When the config has sub-packages and the changed-path list of the merge commit cannot be read, the merge is "not published" (never guess; a warning is logged). The final tag pattern is a FULL match of `<component><separator>v\d+\.\d+\.\d+` (or `v\d+\.\d+\.\d+` when `include-component-in-tag` is false); `-rc.N` candidates and sibling components' tags never prove publication. ## Open questions

Each question names what the Python does today and why the target must decide.

- **Q1 — Pagination.** The Python lists at most 30 open PRs and 30 merged PRs per repo per tick (`limit=30`). On a busy repo PRs beyond the first 30 (by last update) are invisible, and a merged PR beyond 30 within 24 h is never swept. Should the bridge page through all, and what is the per-tick bound?
- **Q2 — Queue order.** The one merge per tick goes to the first mergeable PR in `gh pr list` order ("most recently updated first", per a code comment, not an explicit sort). Should the target order be explicit (oldest first for fairness, or priority), and deterministic when timestamps tie?
- **Q3 — A refused merge consumes the tick.** If the single chosen merge is refused (e.g. 409 head moved, ruleset refusal), the Python still skips all other mergeable PRs this tick. Keep (simple, safe) or fall through to the next candidate?
- **Q4 — Unknown merge state.** The Python treats any merge state other than BEHIND/DIRTY (including `UNKNOWN`, and `mergeable: null` while GitHub computes) as mergeable and relies on the pinned-SHA REST merge and GitHub's own refusal. With REST (`mergeable_state`, `mergeable`) should an unknown/still-computing state wait a tick?
- **Q5 — Assignment.** The Python assigns the ticket to a person/agent in several transitions (reviewer on In Review, author on conflict/rework, escalation human). The `Tracker` trait has no agents. Should adapters assign "back to the PR author" on conflict, red CI, and Done-gate failure (needs author identity mapping), or is status alone enough?
- **Q6 — Native auto-merge.** Keep REQ-MERGE-019/020/021 (opt-in speedup requiring a GraphQL mutation and a local arm-state store) or drop the feature? If dropped, the pass loses nothing in correctness (it merges one PR per tick itself).
- **Q7 — Identifier syntax and URL shape.** The Python hard-codes `<2-5 letters>-<digits>` and `linear.app/<ws>/issue/<ID>`. Livela's identifiers and issue URLs may differ; should the adapter supply the branch/URL/bare-identifier extractors and the "known team keys" notion?
- **Q8 — Ticket unreadable is fail-open for the ticket guards.** When the tracker cannot be read at all (outage, no credential), the Python still merges a green, review-clear PR (the merge decision "does not wait on the tracker"): the business-rule guard is inactive, the zero-boxes guard is skipped, and the Done gate cannot run (the sweep catches the state up later, tracker_synced false). Keep, or fail closed on a tracker outage?
- **Q9 — Contract as a precondition.** Where is the REQ-MERGE-032 contract judgement enforced in the bridge: only inside the Done gate (no boxes at all → refuse Done), also before creating a review round, or also before merging? The Python never reaches a PR with a contract-free ticket in the agent flow (the dispatcher refuses to serve it) but a human PR can.
- **Q10 — Business-rule registry configuration.** The registry path (`docs/business-rules.md`) and the id shape (`BR-<2-6 letters>-<2-4 digits>`) are constants in the Python. Make them per-repo configuration with those defaults?
- **Q11 — What counts as a "statement" in the Business rules section.** Reproduced quirk: a sub-heading with text, a quote line and a table header row are not noise, so they read as new rules when they cite no id; the docstring claims headings and table separators are skipped (only bare ones are). Reproduce exactly, or treat headings/quotes/table rows as noise?
- **Q12 — Triggers and angles.** Which angles exist by default? Does each trigger (needs-review label, unreadable diff, unreadable path list, sensitive path, skipped required check, size) add a specific angle, or only a note in the consolidation item? Should the bridge report ALL matching triggers (Python reports only the first) and the paths per angle? What is the ordered path-to-angle table format (REQ-MERGE-052), and the idempotence key of sub-items (ticket, head SHA, angle)?
- **Q13 — No `.github/review-paths.json` at the base.** Python falls back to a vault table. In the target, a 404: "no sensitive paths", or a `paths` list in `<prefix>-asdlc.toml`, or fail closed? (An invalid or empty file fails closed in all variants.)

The bridge's own repository needs the same property for its Rust sources: what are the markers (e.g. `pulls/{n}/merge`, `merge_pull_request`, `Tracker::set_status`, token env names), and is the list/exceptions format kept?

- **Q17 — Held head.** Is REQ-MERGE-054 ("a head sent back is not sent to review again until a new push") needed in the target, where the coordinator pushes fixes on the PR branch (so heads naturally change)?
- **Q18 — "Latest review" semantics.** Python takes each login's latest review of ANY state, so a later `COMMENTED` review by the same login cancels an earlier `APPROVED`.
