# 2. The repository

Every project has the release cycle (`docs/method.md`): every step below applies, to a project with no optional step too; the optional steps are PR review and release QA (`docs/setup/README.md`, "Optional steps").

**Rulesets** (Settings → Rules → Rulesets):
- `main`: require a pull request, require the status checks `required-check` and the title check (`title / conventional-title` with the example's job id), require branches to be up to date, block force pushes; bypass list: the App only.
- `release/**`: same, bypass list: the App only.
- Tags `*-rc.*` and release tags: block updates and deletions (an RC tag is immutable).

The App on the bypass lists automates the flow; it is never the only actor (`docs/reference/09-requalification-and-human-gestures.md`, BR-ASDLC-021). Who else may merge on `main` and `release/**` is these rulesets' decision, never a workflow's: a person they let merge may merge a delivery PR, an angle PR or the merge-back PR by hand in GitHub, and a person the tag rulesets let tag may tag the release on its candidate and publish it, and the workflows and the bridge take the result as done. `release-publish` accepts a release published by the App or by a person (a User account), and refuses any other bot.

`spl-asdlc doctor` reports one line per ruleset above. `ruleset <default branch>` and `ruleset release/**` (`[release] branch_prefix` followed by `**`) are `ok` when an active branch ruleset that covers the branch requires the status check `required-check` and the title check (a check named `<job> / conventional-title`): the method checks always run and always count (BR-ASDLC-024); the release branches are judged on sample names of the configured shape, so no release branch needs to exist. `ruleset tags` is `ok` when active tag rulesets restrict updates and deletions on every tag the configuration creates. It proves coverage of the configured release and candidate tag templates, rather than accepting a few matching sample refs: use `~ALL`, the template's wildcard form (for example `refs/tags/acme-v*`), `refs/tags/*-rc.*` for candidates, or a literal prefix followed by `*`; an exclusion or an ambiguous pattern is reported `missing` conservatively. A ruleset whose enforcement is `evaluate` or `disabled` counts for nothing and makes its line `invalid`. Patterns are read as GitHub reads them: full refs (`refs/heads/…`, `refs/tags/…`), `~DEFAULT_BRANCH`, `~ALL`, the exclusions winning. The doctor does not judge the other rules (pull request, up to date, force pushes) nor the bypass list, which an App's token reads empty: check those in the settings.

**Secrets**: `SPL_ASDLC_APP_ID`, `SPL_ASDLC_APP_PRIVATE_KEY` (the App), plus whatever the project's publication and deployment steps need. Never a tracker key: the CI does not write to the tracker.

**Variables**: `SPL_ASDLC_RUNNER_READY` (`true` to run the gate on the project's self-hosted runner, otherwise the hosted runner is used for what fits there).

**Workflow callers**: one short workflow per reusable workflow, under `.github/workflows/`, calling `<owner>/spl-asdlc/.github/workflows/asdlc-<unit>.yml@v1` with the project's inputs (test command, suites, runner labels, publication and deployment steps). The callers own the triggers, the concurrency groups and the GitHub environment; the reusable workflows own nothing else. Examples, to copy and edit (replace `<owner>`, the `acme` tag patterns, the App's slug and the `make` commands):

| Example | Calls | Trigger |
|---|---|---|
| `docs/setup/examples/pr.yml` | `asdlc-pr-guards.yml`, the project's tests, the `required-check` action | `pull_request` on `main` and `release/**` |
| `docs/setup/examples/pr-title.yml` | `asdlc-pr-title.yml` | `pull_request`, `edited` included; its own workflow so that a title edit never cancels the tests |
| `docs/setup/examples/release-cut.yml` | `asdlc-release-cut.yml`, which runs the published `spl-asdlc` binary of its channel (`spl-asdlc-version`) | `workflow_dispatch` (`action`, `class`, the reasons, `version` to force one, `dry_run`), dispatched by the bridge |
| `docs/setup/examples/release-gate.yml` | `asdlc-release-gate.yml`, after the project's build | `push` of an RC tag |
| `docs/setup/examples/release-gate-auto-rerun.yml` | `asdlc-release-gate-auto-rerun.yml` | `workflow_run` of `release-gate` |
| `docs/setup/examples/release-publish.yml` | `asdlc-release-publish.yml` twice (`verify`, `close`), the project's publication between | `release: published`; `workflow_dispatch` to resume or replay |

On a draft PR no job of `pr.yml` runs, `required-check` included, so a draft costs no runner minute: every job carries `if: github.event.pull_request.draft == false` (`always() && github.event.pull_request.draft == false` for `required-check`), and a job the project adds gets the same. GitHub reports those jobs skipped, and the ruleset takes a skipped required check as passing; the bridge does not: it counts `required-check` only by its success, so a PR marked ready waits for its `ready_for_review` run.

The file names `release-cut.yml`, `release-gate.yml`, `release-gate-auto-rerun.yml` and `release-publish.yml` are the defaults of `[release] cut_workflow`, `gate_workflow`, `gate_rerun_workflow` and `publish_workflow`: the bridge dispatches and reads them by name. The publication reads `gate_workflow` from the configuration at the release's commit, and the cut at its own, so a caller passes no `gate-workflow`; `doctor` reports a caller that passes one other than the configuration's as invalid. A third-party action is pinned by full commit SHA with its version in a comment, as in this repository's own workflows. The tests under `tests/workflows/examples.rs` check every example against the workflow it calls: inputs and secrets declared, required ones given, permissions granted.

**The workflows' tag**: callers name a moving major tag, `v1`, never a branch. The owner of `spl-asdlc` sets `v1` once the first real caller is green on the commit it names, and moves it forward (`git tag -f v1 <commit>`, then `git push -f origin v1`, by the owner) only for compatible changes: a fix, a new input with a default, a new output. A breaking change gets the next major tag at the commit that introduces it, `v2`, and `v1` stays where it was, so existing callers keep working until they move: an input removed, renamed or made required, a new required secret, a default that changes the behaviour, a called job renamed (check names are an interface, REQ-CI-001), or a called job asking for a permission its callers do not grant. The change's PR says which tag it needs, and its release note says what a caller changes to move. A caller that wants an immutable reference pins the full commit SHA instead of `v1`, or an exact tag `v<X.Y.Z>`, which never moves. A caller may also pin a minor line, `@v<X.Y>` (`@v1.3`): it gets the fixes of that line, every patch `v<X.Y.Z>`, and nothing of the next minor. `v<X.Y>` is moved automatically: the publication of each release `v<X.Y.Z>` (`publish.yml`) moves it to that release's commit once the binaries are attached, never backwards to an older patch, and never moves `v<N>`, which stays the owner's gesture. `v<N>` and `v<N>.<N>` are not crate versions: the crate is tagged `v<X.Y.Z>`, and only those tags build binaries. The tag ruleset of `spl-asdlc` blocks updates and deletions of the exact tags `v<X.Y.Z>` (`refs/tags/v*.*.*`) and must leave `v<N>` movable by the owner and `v<N>.<N>` movable by the publication, which moves it with the workflow's own token: a ruleset on `refs/tags/v*` would block both.

**The process page**: the procedure every agent follows in a project, `docs/agents/process.md` of `spl-asdlc`, is copied into the project's repository at `.spl-asdlc/process.md` (the `process-page` input of `asdlc-pr-guards.yml`), at the version the workflow callers pin. It is never edited there (BR-ASDLC-026, BR-ASDLC-028). Install it, and refresh it at every update of the callers' ref, from the ref they name:

```sh
gh api "repos/<owner>/spl-asdlc/contents/docs/agents/process.md?ref=v1" -H "Accept: application/vnd.github.raw" > .spl-asdlc/process.md
```

Replace `v1` with the minor line `v<X.Y>`, the exact tag `v<X.Y.Z>` or the commit when the callers pin one. `gh` reads a private method repository with its own token; for a public one, `curl -fsSL https://raw.githubusercontent.com/<owner>/spl-asdlc/v1/docs/agents/process.md -o .spl-asdlc/process.md` does the same. Commit the file unchanged, in the same PR as the callers' new ref when they move: its diff shows what changed in the procedure. The project's agent file, `AGENTS.md` at the root (template: `templates/AGENTS.md`), points to the page and holds the project's own instructions around it; when they contradict the page, the page wins. An agent runtime that reads another file name gets a one-line file that points to `AGENTS.md`.

The `guards` job refuses every PR whose page is missing or is not the page of the version it runs at, and its error gives the command above with the callers' ref. The version's workflow carries the page's git blob id, so the check downloads nothing and needs no permission. A caller on `v1` follows the tag: when `v1` moves to a version whose page changed, the project's next PR is refused until a PR refreshes the page, and that PR passes; the release note of such a version says so. A caller on `v<X.Y>` follows its line the same way. A project that wants to choose the moment pins an exact tag `v<X.Y.Z>` and moves its callers and its page together.

**The angle texts**: the agents' review texts (the protocols `docs/agents/review-pr.md`, `review-release.md` and `consolidate.md`, and each angle's `docs/agents/angles/<key>.md`) are not copied into the project. When the bridge creates a review item, it reads them in the method's repository at the ref the workflow callers name, and copies them into that item (BR-ASDLC-032). They are versioned with the workflows: a caller on `v1` gets new texts when `v1` moves, and a caller on `v<X.Y>` at each patch of its line; a caller on an exact tag gets them in the PR that moves its ref, and that PR is where the project sees the update and accepts or refuses it (`git diff <old>..<new> -- docs/agents/` in the method's repository shows what changed). Every caller of the method names the same ref: callers on two refs tell the bridge no version, and it creates no review item. While the method's repository is private, the App's installation must include it (`github-app.md`). `doctor` reports `method version`, `method texts`, and `angle <key>` for each configured angle, `invalid` for an angle the method retired at the pinned version (`docs/reference/08-configuration.md`, "Angles").

**How a candidate is cut**: no release workflow waits for another workflow's run, so the chain works on one runner. `open` (dispatched on `main`) creates the release branch and prepares the release on it with `spl-asdlc release prepare` (`docs/reference/05-release-cycle.md` §1): the version computed from the commits since the last release along the git graph, written into `Cargo.toml` and `Cargo.lock` and the files `[[release.version_files]]` lists, and the version's CHANGELOG section, which is the release notes. It commits `chore(release): v<X.Y.Z>` as the App and pushes the branch and its **first candidate**, `rc.1`, in one atomic push. A range with nothing to release (no Conventional Commit of a type the CHANGELOG lists, no breaking change) is refused, and nothing is created. Every later candidate is a `candidate` dispatched **on the release branch, never on `main`**: `gh workflow run release-cut.yml --ref release/<YYYY-MM-DD-HH-MM>-utc -f action=candidate` (in the Actions UI, pick the release branch in "Use workflow from"), or `spl-asdlc release cut`, which dispatches it there; its version is the one committed on the branch. The first release of a product needs no base tag: tag nothing by hand. With no published release below it, a candidate is measured from the repository's root, its whole history being the delta, and the cut, the gate and the brief say so (`docs/reference/05-release-cycle.md`, "The range and the first release"); its version is bumped from `0.0.0` (a `feat` makes it `0.1.0`) unless forced; `doctor` reports `release base` with the published release the next candidate is measured from, or that there is none yet.

**The binary the cut runs**: `open` downloads a published `spl-asdlc` from the releases of the repository its `spl-asdlc-repository` input names (`<owner>/spl-asdlc`), with the App's token, and checks the archive against the release's `SHA256SUMS` before it runs, as a bridge host does (`bridge.md`, "The binary"). Its `spl-asdlc-version` input names the release: `latest` (the default, the latest published release), a minor line `v<X.Y>` (the newest published release `v<X.Y.Z>` of that line, ranked by version, never by date; refused when the line has none), or a release tag `v<X.Y.Z>` to pin one and move on purpose. A host application that embeds spl-asdlc at `~X.Y` names its line, `v<X.Y>`, so the cut never runs a version outside the embedded one. The runner must be one a binary is published for (Linux x86_64 on the hosted runners; macOS too). `release prepare` reads the checked-out configuration, which the caller names in its `config-file` input (`config-file: .spl-asdlc/config.toml`): the release tag pattern, the version files and the CHANGELOG sections, never an identity, so a neutral file whose identities live in the bridge's instance overlay is enough. The version files and the CHANGELOG sections enter the repository's file only once the installed bridge knows the keys (`docs/agents/process.md`, "Implement a ticket" step 3); until then, the defaults hold. To prepare by hand (the same command the cut runs): `spl-asdlc release prepare --repository <owner>/<repo> --notes notes.md` in a checkout, `--dry-run` to print the version and write nothing.

**What may follow the candidate**: the bridge tags the release on its candidate's own commit; the publication's `verify` stage refuses a release whose commit differs from its candidate beyond that candidate's own QA reports (a person may tag the branch's tip after the last pass), so its inputs repeat `.spl-asdlc/config.toml`: `qa-record` is `[release] record` (its default when the key is left out) and `qa-angles` lists the keys of `[[release.angles]]` (`[]` for a release with no QA angle). They allow the candidate's own angle reports, `<record>/<angle>.json` with `{candidate}` its tag, which the angle PRs land after the candidate; a report of an earlier candidate is refused. An input that disagrees with the configuration refuses a release the GO accepted, and a resume, which rereads the same inputs, cannot recover it.

**Release close**: the publication workflow merges the release branch back into `main` as a merge commit, through the App, which must stay on the `main` bypass list (the merge still waits for `required-check`). A person may do the merge back instead, by merging the merge-back PR as a merge commit: the close takes a merge-back PR merged while it waits, a branch `main` already holds (only deleted) and a branch already merged and deleted as done, and stays green. When the merge back is DIRTY (a real conflict), resolve it off the release branch, never by bringing `main` into `release/**`: cut `chore/merge-back-<stamp>` from the release branch, merge `main` into that branch and resolve there, open its PR into `main` and merge it as a merge commit, then dispatch the publication workflow on the release branch with `replay: true`, which deletes the branch and publishes nothing. Any other block (`required-check` not green, the App refused by the ruleset) is fixed where it is, then replayed the same way.

**Files** (templates in `docs/setup/templates/`, each valid as written and checked by `tests/setup_files.rs`):
- `.spl-asdlc/config.toml` (`docs/reference/08-configuration.md`); `spl-asdlc config check --file .spl-asdlc/config.toml` must pass. Template: `templates/config.toml`, copied to `.spl-asdlc/config.toml`: the configuration with no optional step, the release cycle included, with each layer's keys commented where they go; replace every placeholder, the check cannot tell a placeholder from a real name. A repository that carries no instance data (a public one) commits a neutral file, the method's shape, and leaves the instance keys (the repository, the owner, the team, the logins, the angles' assignees, the release fixer `release.fix_assignee`, the channels) to the instance overlay beside it on the bridge's host, `config.instance.toml` (`bridge.md`); `config check` then passes with the overlay beside the file or named by `--instance`. A key in both files is an error, never an override (BR-ASDLC-014).
- `.spl-asdlc/process.md`, the process page, copied unchanged from the pinned version (above), and `AGENTS.md` at the root, from `templates/AGENTS.md`, its product name replaced and the project's own instructions written under "This project".
- `.gitignore` lists `.spl-asdlc/config.instance.toml`, so that an overlay kept beside a checkout is never committed.
- `.spl-asdlc/business-rules/`, one file per rule, `<ID>.md`, each with the name of the test that proves it (`docs/reference/02-business-rules.md`); absent until the first rule. Template: `templates/business-rule.md`, an example rule copied to `.spl-asdlc/business-rules/BR-<PRODUCT>-001.md` and rewritten, its id in both the file name and the title. A `README.md` index beside the rules is optional. `spl-asdlc doctor` reads every file and names each one whose format is wrong, and its `business-rule tests` line names each test an `Enforced` rule cites that is not in the repository.
- For the release cycle, nothing more: the cut writes the version and the `CHANGELOG.md` itself. A version kept in files besides `Cargo.toml` and `Cargo.lock` is listed under `[[release.version_files]]`; `[[release.changelog_sections]]`, when written, stays equal to the types `asdlc-pr-title.yml` allows (REQ-CI-016).
- `.spl-asdlc/qa/` holds the release QA reports, written by the angle branches. Optional: `.spl-asdlc/angles/<angle>.md` notes.

The ticket skeleton, `templates/ticket.md`, is the contract of `docs/reference/01-ticket-contract.md` for the tracker's ticket template. `spl-asdlc ticket check --description <file>` judges a description before it is served. It reads headings and boxes, not prose, so the unedited skeleton passes it; its Business rules placeholder, though, is read as a stated rule, so a ticket that keeps it is held until `.spl-asdlc/business-rules/` has the rule or the section says `None.`.

**Verify**: `spl-asdlc doctor --file .spl-asdlc/config.toml` reports each item above as `ok`, `missing` or `invalid`.
