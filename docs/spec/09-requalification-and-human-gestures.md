# 09 — Human gestures

The method allows exactly these human gestures in a cycle. Each is a verb or a GitHub action, logged, never an edit of markers by hand.

| Gesture | How | Effect |
|---|---|---|
| **Open a cycle** | `release-cut` workflow dispatch (`open`), or `spl-asdlc release cut --open` which dispatches it | Release branch, prepared (`release prepare`: the version, the version files, the CHANGELOG) and pushed with its first RC in the same run; the bridge creates the issue at the next tick |
| **Tag the next RC** | Same workflow, action `candidate`, dispatched on the release branch (never `main`), or the bridge when the policy automates it | New RC on the release branch |
| **Requalify a finding** | `spl-asdlc release requalify <ticket> --severity <blocker|should-fix|nit> --reason "<text>"` | Changes the finding ticket's severity; adds or removes its `blocks` relation to the release issue; records who, when and why on the ticket and on the release issue; the GO is recomputed at the next tick |
| **Give the GO** (policy `human` only) | Approve on the release issue (a comment `/go` by the owner, or the tracker's approval field when it has one) | Added to the computed conditions; never replaces them |
| **Take an escalation** | The release issue is assigned to the owner with the hold label (created at the first escalation when the tracker lacks it) and the escalation comment when the passes are exhausted | Requalify, allow one more pass (`max_rc_passes` raised for this cycle in the issue), or abandon |
| **Abandon a cycle** | `spl-asdlc release abandon --product <p>` | Keeps the tags, merges the release branch back into `main`, cancels the release issue, turns remaining blockers into tickets |
| **Validate a post-deploy box** | Check the box in the ticket's `## Post deploy` section, once verified in production — the agent of the ticket's validation sub-task, or the owner when the sub-task is reassigned to them | No verb: the bridge moves the ticket from Post Deploy to Done at the tick that finds every box of that section checked |
| **Resume a deployment** | The project's `release-publish` dispatch on the validated RC tag | Project-specific; the bridge reads nothing of it but the merge back that follows |
| **Tag and publish the release** | In GitHub instead of the bridge, as any person the tag rulesets let tag: the annotated release tag on the latest candidate's commit (`git tag -a <release tag> <candidate's commit> -m "Release <release tag>"`, `git push origin <release tag>`), then the release with the version's CHANGELOG section as its notes (`gh release create <release tag> --notes-file <file>`) | The publication accepts it as the GO and says a human gave it; the bridge picks up from the published release (below) |
| **Merge back by hand** | Merge the merge-back PR (merge commit), or the release branch into the default branch some other way that keeps the release tag an ancestor, then delete the branch or let a replay delete it | The publication's close and the bridge's closure take the merge back as done |
| **Take an item or PR over by hand** | Add the hands-off label (`bridge.hands_off_label`, default `spl-asdlc:hands-off`) to the tracker item, or the GitHub label of the same name to the PR; remove it to hand the object back | The tick writes nothing to it: no status, assignment, comment, label, archive or relation on an item; no merge, comment, review dismissal or review round on a PR; no release tag nor release from the GO for a release issue under the label (the person takes the GO). It reports `hands-off: <object>` once per tick. Once the label is gone, the next tick acts on the object as on any other (`07-the-bridge.md`, "Hands off") |

Everything else is either the bridge's or an agent's. In particular nobody writes a status, moves a ticket to Done, or edits a report after it was merged: Done is written by the bridge, at closure or when every `## Post deploy` box of a ticket in Post Deploy is checked. The one exception is an item a person took over with the hands-off label: while it carries the label, its status is theirs, and the bridge writes nothing to it.

## Every step can be done by a human in GitHub

The bridge automates the steps of the flow; it is never the only actor able to perform them (BR-ASDLC-021). A person with write access may do any step below by hand in GitHub, and the chain goes on: every workflow and every tick reads the state GitHub is in, never who brought it there, so a step done by hand is taken as done, neither refused nor redone nor rewritten. Who may merge or push where is the rulesets' decision (`docs/setup/repository.md`), never a workflow's.

| Step | Who can do it today | What a human doing it implies |
|---|---|---|
| **Merge a delivery PR** | The bridge (merge pass: approved, green, current); any person the ruleset lets merge | The sweep gives the ticket the same transition at the next tick, once, and its comment names who merged (`04-pr-review.md` §7, §10); the review round closes. |
| **Merge an angle PR** | The bridge (approved by a coordinator, green, valid report); any person the release branch's ruleset lets merge | The release pass reads it from the PRs merged into the release branch at the next tick: its sub-item Done, the findings of its report filed, once each (spec 05 §5). A report that does not validate is filed by nobody: the bridge says the merged report is unreadable at each tick until a PR on the release branch fixes it. |
| **Cut `open` or `candidate`** | A person, by the `release-cut` dispatch (or the verb that dispatches it); the bridge for `candidate` only when `auto_candidate = true` | None: the dispatch is already a human gesture, and the workflow pushes the branch and the tag as the App so that the gate runs. A tag pushed by hand skips the cut's checks (one cycle at a time, the release class in the annotation): use the dispatch. |
| **Tag and publish the release** | The bridge on its computed GO; any person the tag rulesets let tag | The person takes the GO on themselves: the computed conditions (angles merged, no blocker, the candidate the branch's tip) are the bridge's, and only the publication's own checks still hold (the candidate's gate green, the release tag on the candidate's commit or on a commit that adds nothing but the candidate's own QA reports). The notes are the version's section of the CHANGELOG the cut committed on the release branch: copy it whole, so that the release note of the closure finds each PR's line. `release-publish` accepts a release published by the bridge's App or by a human account (a User), refuses any other bot, and says which in `go-published-by`, `go-published-by-kind` (`app` or `human`) and its summary. A tag the person pushed on the candidate is taken as done by the bridge, which then only publishes the release; once the release is published the bridge tags and publishes nothing more and posts no GO of its own, closes the cycle once it is merged back, and the closure comment records who published the release. To keep the bridge from tagging first, the person adds the hands-off label to the release issue: the bridge then never tags it. |
| **Publication** | The `release-publish` workflow, on the published release; a person, by its dispatch (`resume-from` to redeploy an RC tag) | The project's own jobs publish and deploy; nothing in them depends on the bridge. |
| **Merge back** | The `close` stage, as the App on the default branch's bypass list; a person, by merging the merge-back PR as a merge commit, or by a replay dispatch | The close stage accepts every state a person can leave: the merge-back PR merged while it polls, the branch already held by the default branch (only deleted), the branch already merged and deleted (nothing to merge back); `closing-guard` reads that run green. The bridge's closure waits only for the facts: no release branch holds the candidate, and the default branch holds the release tag. A squash or a rebase loses the tag's commit: it is refused as "nothing carries the release", and the default branch must receive the release branch as a merge commit. |
| **Closure** | The bridge | **Not a GitHub gesture**: the closure writes the tracker (the judged tickets, the release note, the archiving), and is triggered by GitHub facts a person can make (publication, merge back). A release issue closed by hand in the tracker skips the judging and the archiving. |
| **Ticket moves** | The bridge | **Not a GitHub gesture**: a status is the bridge's write (BR-ASDLC-011), derived from GitHub facts. The person does the fact in GitHub (opens, readies or merges the PR, checks a box) and the bridge moves the ticket at the next tick. A person who wants to move a ticket themselves takes it over with the hands-off label: the bridge leaves it as they put it, and acts on it again at the tick after the label is removed. |

*Superseded 2026-10-12 (SID-1058)*: merging the release-please PR by hand, recording a component deployed with the `deployed: production` label, and closing a cycle by waiver (`release close`) are no longer gestures of the method: the cycle has no release PR and supports one version per product, whose release a person tags and publishes as above.
