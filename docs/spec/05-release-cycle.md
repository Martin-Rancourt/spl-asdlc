# 05 — The release cycle

Exhaustive, on the whole project, in release candidates. The bridge coordinates; agents and humans do the QA on branches; the GO is computed.

## Invariants

1. **A human opens a cycle.** The cut is a `workflow_dispatch` of the `release-cut` workflow: it creates the release branch `release/<YYYY-MM-DD-HH-MM>-utc` from `main`, refuses when a release branch is already in flight, and pushes the first RC tag, annotated with the release class. Nothing else happens in CI.
2. **The release issue follows at the next tick.** The bridge sees the new branch and tag, creates the **release issue** (title: product and version read from the release-please PR when it exists, otherwise the manifest), records the candidate on it and labels every embarked ticket `release/<product>-v<version>` whatever its state but Canceled (every merged PR is deployable, `04-pr-review.md` §10). Nothing starts before the issue exists, so a tag without an issue is harmless. The angle sub-items and the brief wait for the gate (§3).
3. **The gate judges the frozen tag.** The `release-gate` workflow runs the project's suites on the RC tag, writes `results/suites.json`, uploads the evidence pack, and fails closed on any skipped or absent suite. QA does not start on a red gate. **Once the candidate's own gate run is green**, and never before, the bridge creates one **angle sub-item** per configured release angle and one **consolidation item** for that candidate (each angle sub-item assigned to its angle's `assignee`, the consolidation item to the coordinator named by `release.coordinator_assignee`, an agent the tracker serves; an unset or unknown participant leaves the item unassigned, and an existing item is never reassigned), then posts the **brief**, which links the gate run and its evidence pack. A red, pending or unreadable gate opens no angle and no brief; each new RC waits for its own gate in the same way.
    **A release may have no QA angle.** A project that writes `release.angles = []` (`08-configuration.md`) runs the cycle without a QA round: the release item, its candidate record, the embarked labels, the gate and its gate-fix tickets, release-please, the publication and the closure are as above; once the candidate's gate is green the bridge opens no angle sub-item and no consolidation item and posts the brief alone, which says that no QA angle is configured. The candidate's record says so too, with the marker `spl-asdlc:no-qa-angle candidate=<tag>`: angles configured later apply from the next candidate, never to one recorded with none. The gate stays: it is the release's minimum.
    **A red gate is never a silence** (BR-ASDLC-016): an **implementer** fixes it on the release branch, from a **gate-fix ticket** the bridge opens. Once the candidate's gate run concluded red and its one automatic rerun of runner aborts and known flakes has settled (the run's latest attempt is a rerun that completed red, or the rerun workflow `release.gate_rerun_workflow` ran for its first attempt and every such run completed; until then the bridge waits, since it cannot read whether a rerun will come), **or no run of the rerun workflow showed up within `release.gate_rerun_wait_minutes` (default 30) of the gate run's completion** (the rerun workflow may be absent or broken: the ticket then says no rerun was seen; a rerun run that showed up and is still running keeps the wait, whatever the bound), the bridge opens **one gate-fix ticket per candidate**, found again by its marker `spl-asdlc:gate-fix candidate=<tag>` among the release issue's children whatever its state, never twice: a child of the release issue, labelled `release/<product>-v<version>`, **unassigned**, in **Ready**, **urgent**, so that an implementer takes it by role. Its contract is complete: the goal is the gate green on the release branch; the failing suites are read from `results/suites.json` of the evidence pack, with the link to the gate run (an evidence pack that cannot be read still opens the ticket, which says the failing suites are unknown and links the run); the non-goals are no new feature and no change beyond what the failure needs; the acceptance is the failing suites passing on the release branch (the listed suites, or the suites that failed in the gate run when they are unknown), an ordinary box the implementer ticks once it verified it on that branch, as any criterion; `No new rule.` under `## Business rules`. The fix is a PR whose base is the release branch (`docs/agents/implement.md` step 2); the next RC is cut by the coordinator, or by the bridge when `auto_candidate = true` (§7). The ticket follows the flow of any ticket: **To Deploy** at its fix's merge (`04-pr-review.md` §10), **Done** at the release's closure (§11). The gate of the next candidate is the verification: when it is red too, the bridge opens a new gate-fix ticket for that candidate, as above. When the gate of the newest candidate is green, the bridge closes every gate-fix ticket of the cycle opened for it or an earlier candidate that never reached a merge, still in Triage, Backlog, Ready or In Progress (a rerun made the gate green, say): **Done**, with a comment naming the green candidate. Any other is left alone: In Review (its PR is being judged), past the merge (the closure judges it, §11) or already resolved. A red gate older than `stagnation_hours` raises the stagnation notice as well, once.
    **Each item carries its protocol** (BR-ASDLC-015), as in a PR review (`04-pr-review.md` §3): beside its contract and what closes it in the bridge's terms, an angle sub-item embeds `docs/agents/review-release.md`, the angle's file `docs/agents/angles/<angle>.md` (or, for an angle of the project's own, a line saying the method has no notes for it) and the schema and rules of the angle report (`06-qa-report.md`); the consolidation item embeds `docs/agents/consolidate.md` and the same schema and rules. The project's angle notes are linked, never embedded. The texts are compiled into the bridge: an item carries the protocol of the bridge version that created it and keeps it while open, since an item found again by its marker is never rewritten; a later candidate's items carry the protocol of the bridge that creates them. An angle sub-item closes when the bridge merges its angle PR (§5); the consolidation item closes with the release at the closure (§11).
4. **Each angle works on its own branch.** The reviewer of an angle cuts `qa/<candidate>/<angle>` from the release branch, reviews the whole project from its angle (with the brief, the evidence pack, the tag annotation and the diff as orientation), commits the fixes of its blocking findings, commits its **angle report** (`06-qa-report.md`, mandatory even when nothing was found), and opens a PR to the release branch whose body names its sub-item.
5. **The coordinator consolidates, the bridge merges.** The coordinator reviews every angle PR: it rejects false alarms with a reason in the thread, confirms severities, resolves conflicts between angle branches, and approves. The bridge merges an approved angle PR into the release branch (merge commit, pinned to the head SHA). A blocking finding an angle could not fix becomes a **blocker ticket** that `blocks` the release issue, created by the bridge from the merged report.
6. **Non-blocking findings become tickets, created by the bridge** from each merged report: one `qa-finding` ticket per `should-fix`; for the `nit`s, as `release.nits` says (`08-configuration.md`), one shared nits ticket per release (`shared`, the default, for a tracker that limits its ticket count) or one ticket per nit in `Triage` (`per-nit`, for a tracker that does not). The agent never writes to the tracker.
    **Everything served to an agent carries a full contract** (BR-ASDLC-012): the bridge writes the nits work as one, never as bare checkbox lines, and no runtime exempts a ticket from the contract by its marker. The nits ticket has a goal, non-goals, the nits as boxes under `## Acceptance criteria` (each one says what was observed, where, and in what context, as the report gives it, and starts with its key `<candidate>/<angle>/<finding id>`), and `No new rule.` under `## Business rules`. Its goal is to **triage**, not to fix: the agent who takes it up at refinement classifies each nit as kept or dropped, never presuming it fixed; a kept nit becomes real work, a dropped nit is closed with its reason. The bridge adds the box of a later nit to the shared ticket at the end of its `## Acceptance criteria`, never twice for one key, and never into a nits ticket that carries no contract (an older format): that ticket is left alone and said at each tick, fail-closed. A per-nit ticket is found again by its finding marker, like a `qa-finding` ticket.
7. **Every merged fix tags a new RC.** After angle PRs are merged, the next RC is tagged (by the coordinator through the cut workflow's `candidate` action, or by the bridge when the project's policy says so), the gate runs again, and the configured policy says whether the angles review again: by default, **full QA on every RC** until `max_rc_passes` is reached; a project may choose "gate and coordinator only" for the following passes.
8. **The GO is computed.** All at the latest RC: gate green; every angle PR of this RC merged (or, for a later pass under the lighter policy, every angle of the first pass merged; for a candidate with no QA angle, this condition does not apply); zero open blocker (no ticket `blocks` the release issue, no angle PR open with a `hold`); the release-please note covers every commit of the range; the staged version equals the version the QA judged. Nobody gives the GO, unless the project's policy is `human`, in which case the bridge waits for the owner's approval on the release issue in addition to the computed conditions.
9. **The bridge merges the release-please PR** (squash, pinned to its head) on GO; for a multi-component product it merges the record PR first, then each component's release PR, the version component last. The merge is the signal: the `release-publish` workflow runs on the published release, verifies that the RC's gate was green and that only bookkeeping changed since the RC, runs the project's publication and deployment steps, labels each deployed component `deployed: production`, merges the release branch back into `main` (never `main` into the release branch), deletes the branch, and fails if the merge-back or the guard was skipped.
10. **Escalation when the passes are exhausted.** If blockers remain after the last allowed RC pass, the bridge assigns the release issue to the owner with a hold label and a comment that lists the blockers. The owner may requalify a blocker (`09-requalification-and-human-gestures.md`), abandon the cycle, or allow one more pass.
11. **Closure is triggered by facts.** When the bridge sees the release published (single component) or every embarked component labelled `deployed: production` (multi-component), and the merge-back merged, it closes the cycle: each embarked ticket in To Deploy or Post Deploy whose latest merged PR is in this release's range is judged (a ticket whose next PR merged after the cut is left to the release that ships it, spec 04 §10; every box ticked → **Done**; only `## Post deploy` boxes open → **Post Deploy**, with a **validation sub-task** created under it, unassigned, in Ready, **urgent**, since production is waiting on it (BR-ASDLC-017); otherwise → **In Progress**, **unassigned**, with the list of what remains); an embarked ticket In Progress or In Review shipped a PR that did not close it and is left to its next PR; each business rule cited by an embarked ticket is verified against the registry at the release tag, fail-closed (a cited rule the registry lacks sends the ticket back to **In Progress**, unassigned too); a ticket the closure sends back is never kept on its current assignee nor handed to someone named: rework is distributed by being pickable, and the agent system resumes it by role (BR-ASDLC-009); the release issue is closed with the summary; the **record** (the merged angle reports) is now on `main`. **Once the release issue is closed, the bridge archives what the cycle resolved** (BR-ASDLC-019), so that a tracker that counts its open items against a limit (Linear's free plan) keeps room for the next cycle: the resolved children of the release issue (its angle sub-items, its consolidation item, any other child such as a gate fix), the nits ticket once resolved, the resolved PR review round items (angle sub-items and consolidation items, recognised by their bridge markers) of the embarked tickets, and the embarked tickets the closure moved to **Done**; the release issue goes last. It **never archives an open item**: a ticket in Post Deploy (and its validation sub-task) or In Progress, a finding in Triage, an open nits ticket stay; nor an item with an open sub-item, nor an item in a state the status table does not place, and the release issue waits while one of its children is open. An archived item stays searchable and restorable; one already archived is skipped, so a second tick writes nothing. A failed archive is reported and retried at the next tick (the release issue, archived last, keeps the cycle in view until then); it never blocks nor undoes the closure. A release issue closed by hand, without the closure, is not archived from, and a tracker without an open-item limit (Livela) archives nothing.
    A ticket in **Post Deploy** is never served itself: its validation sub-task is. The agent that takes it verifies the ticket's `## Post deploy` boxes in production, checks on the ticket the ones it can verify, and closes the sub-task; a check that needs a human, or is beyond it, is named in a comment and the sub-task is reassigned to the owner, who finishes. There is no verb: the bridge moves the ticket from Post Deploy to **Done** at the tick that finds every box of its `## Post deploy` section checked (the same Done gate as the closure's), and leaves it in Post Deploy while one box is open.
12. **The release note is part of the deliverable.** The bridge builds it from the release-note snippets of the shipped tickets (and the release-please changelog for what has no snippet), and sends it through the configured channels. A failed send is a failed closure step, retried, never dropped.
13. **Abandoning a cycle** keeps the RC tags, merges the release branch back into `main` so that merged fixes are not lost, cancels the release issue, turns each remaining blocker into a ticket, and the next cut starts a new cycle from `main`.
14. **A release the bridge did not open is not its cycle.** A version already published with no release issue of the bridge (a release made before the bridge took the product over) is left alone: no issue, no closure, no note. The bridge's first cycle on a product is the first one cut after it took over.

## The brief

Posted by the bridge on the release issue once per RC, once that RC's gate is green (§3): the candidate (tag, commit, class), the range, the embarked tickets with their acceptance criteria (each ticket is found by commit → PR → linked ticket, never by text), the business rules touched (registry rows whose paths or tests intersect the range), the link to the evidence pack, the angles and their sub-items. A range, PR, link or evidence pack that cannot be read makes the brief fail; it is never guessed or left empty, and the angle sub-items wait with it, so that no agent starts without its brief.

## Configuration (per project)

- Release shape: candidate tag pattern, final tag pattern, components and their release PRs, the record file, the version component.
- Release angles with assignee hints, or `angles = []` for a release with no QA angle (§3); the tracker participant who receives the consolidation item (`release.coordinator_assignee`, optional); `max_rc_passes` (default 2); the policy for later passes (`full` | `gate-and-coordinator`); GO policy (`computed` | `human`); the nits grouping (`shared` | `per-nit`), chosen for the tracker.
- Publication and deployment steps (inputs of `release-publish`); the deployment truth (`deployed: production` labels by component).
- Notification channels for the release note.
